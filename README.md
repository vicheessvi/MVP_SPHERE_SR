# MVP_SPHERE_SR

Локальный инструмент инвентаризации, автоматического опроса и аналитики терминалов ВКС, контроллеров, панелей управления и другого мультимедийного оборудования. Внешняя передача данных, телеметрия, CDN и облачные сервисы не используются.

## Требования и запуск

Для полного режима нужен установленный **Python 3.11 или новее**. Node.js, PowerShell, CMD, `pip`, виртуальное окружение, инсталлятор и права администратора не требуются.

1. Скачайте или скопируйте весь проект в любую локальную папку.
2. Дважды щёлкните `START_MVP_SPHERE_SR.py`.
3. Не закрывайте открывшееся окно Python во время работы: локальный исполнитель действует только пока оно открыто.

Если Windows впервые спрашивает, чем открыть `.py`, один раз выберите установленный `python.exe`. Скрипт проверит версию Python и целостность обязательных файлов, запустит случайный адрес `127.0.0.1` и откроет браузер с одноразовой локальной сессией.

При первом открытии раздела «Загрузка данных и опрос устройств» на каждом ПК задайте собственные логин и пароль для плана опроса (пароль от 12 символов). При следующих запусках войдите с ними; кнопка «Закрыть доступ к плану» завершает доступ текущего запуска. Проверку выполняет локальный Python runtime: до входа он не принимает учётные данные оборудования и не запускает опрос. В профиле текущего пользователя Windows, `%LOCALAPPDATA%\MVP_SPHERE_SR\admin-access.json`, хранится только соль и проверочное значение пароля; открытый пароль не записывается в проект или Git. На другом ПК пароль задаётся заново. Для сброса забытого пароля необходимо отдельное явное действие с локальным файлом; автоматического обходного входа нет.

Прямой двойной щелчок по `index.html` сохраняется как отдельный ручной режим: загрузка SR, общей папки JSON и аналитика работают, автоматический сетевой опрос недоступен.

## Интерфейс и данные

Доступна одна роль — «Администратор МЦТП». Основные разделы: «Главный экран», анализ перезагрузок, версий проектов и прошивок, ошибки при подключении, «Оборудование» с семью категориями, «Загрузка данных и опрос устройств», «Локальное хранилище» и «Справочник». Анализ перезагрузок раскрывает таблицы по нажатию на карточки; версии сравниваются по истории точно сопоставленного устройства, а ошибки авторизации и сети показываются раздельно. «Сравнение полей файлов опроса с параметрами SR» остаётся в разработке. Модули «Проекты аудита», «События», «Сопоставления» и «Снимки» в навигации отсутствуют.

Оборудование всегда строится из актуальной выгрузки SR. Все строки SR сохраняются, включая неполные записи без inventory, serial, MAC или IP. Разные устройства не объединяются по похожему адресу или имени: новый JSON автоматически привязывается только к точному текущему IP из актуальной SR. Исторические IP используются лишь для диагностики.

Актуальная выгрузка SR содержит 42 столбца: от `SmartRoom ID локации` до `802.1x`. Основные новые названия — `Наименование локации`, `Адрес локации`, `Класс оборудования`, `Наименование оборудования`, `Тип`, `IP адрес` и `MAC адрес`. Прежние заголовки принимаются как совместимые псевдонимы. Если в строке есть `SmartRoom ID локации` или `SmartRoom ID оборудования`, они используются как устойчивые идентификаторы при последующих загрузках; исходная строка XLSX сохраняется без изменения.

Результаты ручного опроса загружаются общей папкой. Внутри неё ожидаются одна или несколько папок запусков:

```text
polling-export/
├── 2026-06-01_09-41-28/
│   ├── 192.0.2.10.json
│   └── 192.0.2.11.json
└── 2026-06-02_10-15-00/
    └── 192.0.2.12.json
```

Имя `2026-06-01_09-41-28` означает 1 июня 2026 года, 09:41:28. JSON ищутся рекурсивно. Время отдельного результата берётся из `File.lastModified`, а не подменяется временем папки.

## Автоматический опрос

### Отдельный список устройств и выбор действий

В разделе 4 выберите источник: актуальная SR или «Загруженный список XLSX».
Список использует существующие колонки SR/таблицы работы с портами; он не
заменяет основную SR и не добавляет строки в аналитику. Если листов несколько,
отметьте один или несколько и нажмите «Загрузить выбранные листы». Ни один лист
не выбирается автоматически. Некорректный лист или повторный IP блокируют весь
выбранный набор; вспомогательный лист можно не выбирать.

Выбранный XLSX остаётся видимым в текущем сеансе при перерисовке формы и обновлении
панелей БД. Состояние показано непосредственно под полем: чтение, выбор листов,
успешная загрузка с числом устройств либо конкретная ошибка. Для повторного
выбора того же исправленного файла нажмите «Сбросить выбор списка» и выберите
его заново. Это очищает только временный список целей, не рабочую БД и не файл
на диске; после F5/нового запуска список нужно выбрать повторно.

Далее выберите фильтры/точный IP и действия: JSON-опросы, сбор логов, доступное
изменение параметров либо разрешённое сочетание. По умолчанию всё выключено,
настройки стоят «Не менять». **Выполняется только выбранное в разделе 4**:
значения колонок XLSX не задают команды. Для «только логи»/«только изменение»
полный JSON-опрос не выполняется; служебные проверки модели/идентичности и
контрольное чтение изменяемого поля обязательны. Несовместимая задача у одного
из выбранных устройств блокирует план, не превращается в другую операцию.

Проверьте список целей и итоговое подтверждение с листами, числом устройств и
точными действиями. При смене файла или источника действия нужно выбрать заново.
Для «только изменение» явно выберите папку служебного журнала: в папке запуска
будет только `polling-recovery.json`, без JSON-опросов устройств и логов.
Для восстановления загрузите тот же XLSX с теми же листами (либо исходную SR),
выберите прежнюю папку и повторно введите учётные данные. Продолжается исходный
план, не текущий выбор формы; неясные записи автоматически не повторяются.
Прежние модельные ограничения изменений, отдельное согласие и локальный вход
сохраняются. В `file://` сетевые действия по-прежнему недоступны.

### Подтверждённые модельные контракты

Для смешанного списка можно одновременно выбрать Answer mode нескольких
контрактных групп. У каждой группы свой переключатель и целевое значение;
у Polycom отдельно задаются Point-to-Point и Multipoint. В таблице «Проверить
выбранные цели» есть столбец «Действия плана», а в подтверждении — числа по группам.
«Не менять» не вызывает write. Если JSON и логи не выбраны, такие устройства
вообще не опрашиваются и считаются отдельно как «Без выбранных действий», не
как успешно изменённые. При выбранных JSON/логах с них собираются только эти
данные. Устройства обрабатываются по очереди; интервалы — между обращениями.
HTTP, NTP, SSH, питание и другие виды изменений с таким планом не совмещаются.
Старые планы v3/v4 сохраняют прежние действия и не расширяются при продолжении.

Answer mode exact TE20, TE30/TE40/TE50/TE60, Huawei Bar 310/Box 310/Box 610 и Bar 300/Box 300/Box 600 можно изменять для одного IP либо для совместимой группы по фильтрам выбранной SR либо списка XLSX. Новый Answer mode план v5 допускает несколько контрактных групп: каждому устройству назначается только явно выбранное действие его семейства. Неизвестная модель или несовместимое назначение блокируют план целиком. Перед запуском инструмент показывает количество целей и запрашивает согласие на изменение входящих вызовов. Устройства обрабатываются последовательно, каждое со своим чтением до/после максимум одной записи и служебным результатом (JSON-файл — только при выбранном JSON-опросе); неясная write-операция автоматически не повторяется. Ранее подтверждённые одиночные и массовые сценарии TE/310 сохраняются. 24 ноября 2026 года администратор дополнительно подтвердил оба направления Answer mode по одному IP и массово на Bar 300, Box 300, Box 600 и Polycom RPG 300/310/500/700.

Для точных Huawei Bar 310, Box 310 и Box 610 при выборе одного IP или совместимой группы фильтрами доступны три варианта Answer mode: «Не менять», «Автоматически — включить автоответ», «Вручную — отключить автоответ». Изменение запускается отдельно от HTTP и других write-задач, требует подтверждения и проверяется чтением до и после максимум одной записи на устройство. На Bar 310 оба направления проверены контролируемым циклом с восстановлением исходного режима; администратор подтвердил обе стороны в одиночном и массовом режимах также для Box 310/610. Обычный опрос настройку не меняет.

Для Huawei Bar 300, Box 300 и Box 600 три варианта находятся в том же блоке плана. На Bar 300 проверены оба направления `autoreply=0↔1` с возвратом исходного «Авто»; это обратная кодировка относительно серии 310. При отсутствии точной модели/схемы запись не отправляется, при неясном ответе не повторяется. Администратор отдельно подтвердил изменение Answer mode всех трёх моделей в обоих направлениях по IP и массово; новые write-результаты имеют `confirmed_user_validation`. Исторические JSON не переписываются.

Для Polycom RPG 300/310/500/700 администратор 24 ноября 2026 года также подтвердил
оба направления Answer mode, отдельно по IP и массово. Point-to-Point и Multipoint
остаются независимыми выборами; «Не менять» не создаёт запись. Новые write-результаты
имеют `confirmed_user_validation`, исторические JSON не переписываются. Старые
HTTPS-несовместимые прошивки Group 300 по-прежнему не получают HTTP fallback.

Для точного Huawei Bar 310 поле `autoUpdate` в JSON отражает подтверждённую администратором **возможность обновления прошивки** по меню «Сервер → Основные службы → Тип сервера»: «Вручную» — отключено, другой доступный вариант — включено. В результате сохраняются источник и `meaning=firmware_update_capability`; это не запись о том, что обновление уже выполнялось. Администратор отдельно подтвердил имена и значения параметров Box 310 и Box 610; новые результаты обеих моделей теперь подтверждены, старые предварительные файлы остаются без изменений.

В плане можно независимо включить «Формировать JSON-опросы» и «Собирать логи устройств»: только JSON, только логи или оба режима. Для логов выбирается отдельная папка с папкой времени запуска; в режиме только логов JSON устройств не создаются, но видимый `polling-recovery.json` остаётся. Сбор подтверждён администратором для TE20/30/40/50/60, серии 310 и теперь также Bar 300/Box 300/Box 600. Серия 300 использует отдельный guarded XML-экспорт через существующий потоковый механизм; пользователь подтвердил успешное формирование опросов и логов на всех трёх моделях. Папку можно импортировать вручную: отображаются метаданные и точное сопоставление IP без раскрытия содержимого или распаковки архивов. Для серии 300 позднее добавлено собственное подтверждённое событийное правило; правила TE/310 на неё не переносятся. Исторические предварительные результаты не переписываются.

После «Импортировать папку логов» модуль «Анализ перезагрузок устройств» отдельно показывает подтверждённые перезагрузки, зафиксированные отключения и предполагаемые отключения питания точных Huawei TE20/30/40/50/60. Предположение имеет низкую достоверность: перед неизвестным запуском долго не было записей, по умолчанию 60 минут; порог можно изменить. Это не доказательство потери питания, и предполагаемые случаи не входят в подтверждённые итоги. Повторные выгрузки не удваивают события. Время остаётся локальным временем терминала, момент потери питания неизвестен. Сырые строки логов не сохраняются в аналитике; TE20 использует отдельное правило web reboots → System boot и различает штатное выключение через web и с пульта ДУ; Extron сохраняет своё прежнее правило.

Для точных Bar 310, Box 310 и Box 610 в этом модуле отдельно выводятся перезагрузки, штатные выключения, запуски после выключения и запуски без установленной причины со способом Web или пульт ДУ. Web-перезагрузка требует успешной команды и последующего System boot; пультовая — двух близких нажатий кнопки питания и следующего boot без команды выключения. Штатное выключение с пульта требует отдельной команды `user shut down terminal` после нажатия. Внутренние `restart` компонентов и паузы без строк не считаются доказательством перезагрузки или потери питания. Администратор подтвердил правильность анализа Box 310 и Box 610 на рабочих устройствах; точная модель и IP проверяются при импорте.

Страница аналитики теперь содержит внутренние разделы «Анализ перезагрузок» и «Анализ отключения питания». Во втором разделе Bar 310, Box 310, Box 610, как и TE, могут показать только низкодостоверное предположение по паузе в журнале не менее часа перед неизвестным запуском. Кольцевая диаграмма берёт за 100% все устройства текущего фильтра и распределяет каждое не более чем в один интервал по максимальной завершённой паузе: до часа, до суток, до недели, до месяца, до 3 месяцев, до 6 месяцев, до года, более года. Устройства без измеренного интервала остаются в отдельном сером секторе; по умолчанию выбран «Более года». Подтверждённые команды выключения и предполагаемые паузы отмечаются разным основанием. Отсутствие логов не является доказательством отсутствия питания; диаграмма не показывает текущее состояние устройства.

Тепловая карта в разделе питания показывает день недели × час по локальному времени терминалов. Переключатель отделяет подтверждённые штатные выключения от предполагаемых пауз; цвет ячейки означает число уникальных устройств, а не повторных записей. Нажатие раскрывает устройства, локации и файлы-источники. Карта следует текущим фильтрам и периоду событий. Часовые пояса устройств не выравниваются без подтверждения, а совпадение времени не доказывает общую причину.

В обоих внутренних разделах доступен отдельный срез терминалов ВКС со статусом оборудования «Учёт» из актуальной SR. Два кольца, три TOP-5 и тепловая карта позволяют открыть списки по подтверждённым перезагрузкам, штатным выключениям и предполагаемым паузам, не смешивая их достоверность. Домен, производитель, модель, VIP, локация, адрес и период меняют всю выборку. Кнопки скачивают два локальных XLSX: перезагрузки и питание; в файле питания штатные выключения и предположения имеют разные столбцы. Серый сектор означает отсутствие выявленного события либо неподдерживаемый разбор, а не исправность. Архивы Polycom `.tgz` пока импортируются только как метаданные и не создают событий.

Для одного exact Huawei TE20 из текущей SR управление питанием позволяет оставить без изменений либо выбрать Shut Down/Restart, сон «Никогда» или 1/5/10/15/30/60 минут и плановый перезапуск. Включение расписания требует явного времени ЧЧ:ММ. После отдельного подтверждения исполнитель читает пять полей, отправляет максимум одну запись только изменённых значений и проверяет точный результат. Администратор подтвердил корректную работу новых параметров на рабочем TE20; обычный опрос остаётся read-only.

Для одного exact Huawei TE20 из текущей SR три поля NTP позволяют отдельно выбрать включение синхронизации, режим «Авто/Вручную» и новое имя сервера либо оставить каждое без изменений. При наличии хотя бы одного изменения требуется отдельное подтверждение; исполнитель проверяет модель, читает текущие значения, делает не более одной ограниченной записи и повторно читает все три поля. Сервер вводится только для ручного режима и ограничен 41 символом. Администратор подтвердил корректное изменение всех трёх показателей на рабочем TE20; обычный опрос остаётся read-only.

Для одного точного Huawei TE20 из актуальной SR поле SSH предлагает «Не менять», «Включить» или «Отключить». Изменение выполняется отдельной задачей после подтверждения, с чтением до и после максимум одной записи. Отключение может прекратить удалённый доступ. Администратор подтвердил работу включения и отключения SSH на рабочем ПК; другие модели не затронуты.

Для одного точного Huawei TE20, выбранного по IP из актуальной SR, поле «Автообновление» предлагает «Не менять» (по умолчанию) или «Отключить». При выборе отключения требуется отдельное подтверждение: локальный исполнитель читает настройку до записи, при необходимости записывает только её и повторно проверяет значение. Обычный опрос не меняет настройку. Администратор подтвердил работу отключения на рабочем ПК. С другими задачами изменения оно не совмещается.

В модуле «Загрузка данных и опрос устройств»:

1. при первом запуске настройте доступ к плану, затем входите с выбранными логином и паролем; подключите отдельную рабочую папку через «Обзор», чтобы импортированные данные восстанавливались после закрытия браузера;
2. выберите актуальную SR либо загрузите отдельный список XLSX и подтвердите его листы в разделе 4;
3. выберите нужные действия и папки для выбранных результатов (для одного изменения — папку служебного журнала);
4. введите пары логина и пароля устройств в нужном порядке; при необходимости добавьте или удалите строки и передайте пары локальному исполнителю;
5. сформируйте план Домен → Класс оборудования → Производитель → Модель, задайте время и границы случайного интервала в секундах (например, от 5 до 10 включительно); для трёх и более поддерживаемых устройств границы должны различаться, кроме режима 0–0 без пауз;
6. при диапазоне 0–0 прочитайте предупреждение и подтвердите запуск без пауз; затем нажмите «Сформировать и запустить опрос».

Python-runtime сверяет SHA-256 переданных пар, держит их только в памяти одного задания и очищает после завершения, отмены или ошибки. Поля ввода очищаются сразу после передачи; итоговые JSON, журнал восстановления и аналитика секретов не содержат. При выбранных JSON-опросах каждый redacted JSON сохраняется браузером в выбранную папку `YYYY-MM-DD_HH-mm-ss`. Если один JSON записать не удалось, ошибка фиксируется и остальные устройства продолжают опрашиваться. Если браузер закрылся или компьютер перезагрузился, заново запустите инструмент, выберите прежнюю общую папку, повторно загрузите исходную SR либо тот же отдельный XLSX с теми же листами, снова введите пары и нажмите «Продолжить опрос». Сохранённые файлы проверяются по точному IP и не опрашиваются повторно. Неясный исход задачи изменения настроек автоматически не повторяется и требует отдельной проверки. Видимый `polling-recovery.json` создаётся в папке запуска и не импортируется как опрос устройства.

В разделе «План автоматического опроса» отдельный XLSX-список и папка готовых JSON позволяют скачать локальную таблицу фактических настроек. Значения выводятся только при точном совпадении IP, модели и подтверждённого адаптера последнего успешного опроса. Обычный опрос читает HTTP/Telnet у Huawei TE20–TE60; у exact CloudLink Bar 310/Box 310/Box 610 — Site name, автоответ, NTP, Wi‑Fi, SSH и подтверждённые поля питания. Администратор отдельно сверил имена и значения обеих Box, поэтому новые JSON входят в XLSX и таблицу Site name как подтверждённые; старые provisional-файлы сохраняют «Требует проверки». У exact TE20 дополнительно читаются SSH, автообновление, автоответ, NTP и питание. Неподтверждённая настройка не заменяется значением по умолчанию. Отчёт не меняет устройство; отдельные write-задачи по-прежнему требуют явного согласия и собственных модельных контрактов.

Подтверждены локальные автоматические опросы контроллеров/панелей Extron и терминалов Huawei TE20/TE30/TE40/TE50/TE60/Bar 310/Box 310/Box 610. TE20 использует отдельный HTTPS/443 transport с legacy TLS 1.1 и проверкой модели. TE30/TE40/TE50/TE60 используют общий guarded web-CGI transport. Bar 310, Box 310 и Box 610 теперь используют один `huawei_310_rest_v1` / `huawei-310-rest-v1` на основе Bar 310 при сохранении точной проверки каждой модели до credentials и после входа. Модельные ключи и старые JSON сохранены; объединение не подтверждает предварительные настройки Box. Самоподписанный сертификат разрешается только явно для текущего задания; HTTP fallback отсутствует. Неподдерживаемые модели остаются `protocol_required`. Выключенная по умолчанию задача закрытия HTTP/Telnet доступна точным TE20–TE60 и по модельным правилам серии 310 через отдельный список целей; обычный опрос серии 300 остаётся read-only, а Answer mode меняется только отдельной opt-in задачей, описанной выше.

Для терминалов Huawei дополнительное Site Name считывается только после точной проверки модели и идентичности. TE20, серия 300 и Bar 310 используют проверенные модельные способы; значение Bar 310 посимвольно сверено с web-меню. Имена сайта Box 310 и Box 610 подтверждены администратором отдельно, поэтому новые успешные результаты доступны в таблице Site name; исторические provisional-файлы автоматически не повышаются. При несовпадении схемы сохраняется `protocol_required` или `unavailable`; имя локации SR никогда не подставляется вместо значения устройства.

Huawei CloudLink Bar 300 использует проверенный read-only HTTPS web-CGI опрос с проверкой модели до и после входа, устойчивого идентификатора и текущего bundle. Общий узкий reader новых настроек действует также для exact Box 300 и Box 600 с их собственными модельными проверками. Администратор подтвердил успешные опросы всех трёх устройств и совпадение новых значений Box с меню; новые поля Box теперь подтверждены. Исторические предварительные файлы не переписываются. Ни одна модель серии 300 не наследует REST-контракт или команды серии 310. Единственное отдельное исключение для записи — собственный CGI Answer mode по ADR-0056; остальные management write не добавлены.

Администратор подтвердил отсутствие SNMP v2 в меню серии 300 при SNMP v3 по умолчанию. Отчёт показывает «SNMP v2 не поддерживается (не используется)», не утверждая, что вся служба SNMP выключена или порт закрыт.

Поле «Автообновление» читается из «Сервер → Основные службы → Тип сервера»: «Вручную» (в текущей локализации «Руководство») соответствует отключённой возможности обновления прошивки, остальные доступные варианты — включённой. Код ручного режима 7 подтверждён на Bar 300; администратор отдельно сверил фактические значения Box 300/600 с их меню. Это не означает, что обновление уже выполнялось.

В «Управлении питанием» exact Bar 300 подтверждён интервал сна: сохранённый код 10 означает 10 минут и попадает в JSON. Остальные переключатели проверяются отдельно и не подменяются значениями со снимка.
Четыре видимых переключателя питания также читаются отдельными узкими запросами: на контрольном Bar 300 Wake-on-LAN, пробуждение по лицу, очистка во сне и автоперезапуск вернули код 0, совпавший с «Запрещать». При включённом автоперезапуске его период потребуется проверить отдельно; сейчас режим выключен.

## Хранение и защита

Локальный запуск теперь использует DB-first экраны: в браузер приходят сводки и страницы оборудования, опросов, версий, ошибок и событий. Вся история больше не собирается в память вкладки после входа. При первом открытии старой базы появится «Создаём быстрые индексы»; это разовая подготовка сохранённых данных, а не повторное чтение логов. Её можно продолжить после закрытия браузера.

Диаграммы и TOP считаются по всей выборке, таблицы открываются страницами. Выбор даты, часа, устройства или сектора уточняет запрос к БД. Журнальные события и расчёты Date − Uptime доступны отдельно. Подтверждённые выключения и предполагаемые паузы остаются раздельными. XLSX включает все строки выбранной области, не только видимую страницу. Часть тяжёлых сводок на миллионе записей может рассчитываться несколько секунд; в это время можно менять модуль.

«ВКС Учёт: перезагрузки XLSX» содержит только подтверждённые по журналам перезагрузки. «ВКС Учёт: питание XLSX» содержит штатные выключения и предполагаемые паузы отдельными показателями/датами/достоверностью, без столбцов перезагрузок. Общие поля устройства сохраняются; устройство с обоими видами событий может быть в обоих файлах. Экспорт использует применённые фильтры на момент нажатия и одну БД/revision. «Причина запуска неизвестна» означает маркер запуска без достаточного подтверждения причины; сам по себе он не считается подтверждённой перезагрузкой или потерей питания. Правило предполагаемой паузы применяется отдельно.

### ВКС «Учёт»: нерабочее время

#### Обновление правил Shut down

Если перепроверка встретила проблему в файле, проверка остальных продолжается.
Под импортом появляется таблица с относительным путём, кодом причины и действием;
в счётчиках видны готовые разборы и число проблем. Вспомогательный файл либо
старый файл, который никогда не был успешно разобран, не блокирует остальные.
Корректное окончание XML с длинным пробельным хвостом принимается.

Если нельзя заново подтвердить файл с прежними событиями, частичная замена базы
не публикуется: старая аналитика остаётся активной. Все остальные готовые разборы
сохранены для продолжения. Проверьте доступ к указанному файлу либо получите
корректный исходный экспорт, затем выберите ту же полную папку и нажмите
«Продолжить импорт логов». Не удаляйте базу, не переименовывайте логи ради
сопоставления и не дописывайте закрывающие теги вручную. При недоступном исходнике
сохраняйте старую базу: исключение доказательств требует отдельного решения.
В локальном режиме с рабочей базой после обновления страницы готовые текущие scans не читаются заново целиком;
проверка прочитает только ещё не завершённые/изменившиеся файлы. Ошибка не оставляет
план опроса заблокированным, если его SR уже опубликована и контекст подтверждён.

Для поддерживаемых Huawei TE20/30/40/50/60, Bar 310/Box 310/Box 610 и
Bar 300/Box 300/Box 600 зарегистрированная команда выключения всего терминала
учитывается независимо от того, кто её отправил: пользователь или контроллер.
Web-маркер и кнопка пульта больше не обязательны. Ошибки, отмена, настройки/меню
и выключение отдельных компонентов не увеличивают счётчик. Инициатор не
угадывается; Web/ДУ показывают канал записи, а не доказанного пользователя.
Команда учитывается как штатное выключение, отдельно от предположений по паузам
и без утверждения об аварийной потере напряжения.

**Для этого обновления правил нужна однократная перепроверка прежних логов.**
В БД нет исходных строк, поэтому пропущенные команды нельзя получить только
пересчётом SQL. После перезапуска обновлённого runtime подключите ту же БД и в
модуле загрузки выберите **полную прежнюю папку логов**. Перепроверка включится
автоматически при обнаружении старой версии правил; SR и JSON заново импортировать
не нужно, опрашивать устройства тоже не нужно. Исходники остаются неизменными.

Во время перепроверки видны прогресс/скорость/ETA. Старая опубликованная аналитика
не заменяется частичной. После сбоя снова выберите ту же папку, ту же SR и тот же
режим: готовые scans новой версии восстанавливаются без чтения тела (префиксы
проверяются). Успешное завершение публикует новые события для всех существующих
диаграмм, карт и XLSX. Неполная/ошибочная перепроверка не удаляет прежние итоги.
Polycom RPG оставлен на отдельный этап после подключения устройства; TGZ пока
участвует только как метаданные, без событийной аналитики.

#### Работа со срезом

В локальном режиме с подключённой БД откройте «Анализ перезагрузок устройств →
ВКС «Учёт»: нерабочее время». По умолчанию — последние два календарных месяца
и группа «Выключения не зафиксированы». Отдельное кольцо «Одно штатное выключение»
открывает устройства, у которых ровно одна подтверждённая команда в выбранное
нерабочее время. Учитывается только статус **оборудования** «Учёт» в актуальной SR.

Календарь — федеральная пятидневка РФ с переносами: выходные и праздники целиком.
В рабочие дни рабочее время 07:00–18:00, нерабочее — 00:00–07:00 и 18:00–24:00.
Перенесённая рабочая суббота считается рабочим днём. Проверены 2024–2027 годы, за их пределами расчёт явно
блокируется до обновления календаря. Региональные праздники не добавляются.
Можно изменить даты, домен, производителя/модель, VIP, локацию/адрес, группу и
вид нерабочего времени. Кольца кликабельны. Карта 7×24 показывает только времена
зарегистрированных событий группы; клик часа уточняет список. TOP-5 показывает
подтверждённые перезагрузки этой группы в нерабочее время.

«Скачать выбранную группу XLSX» выгружает весь список, а не одну страницу.
Перезагрузки, штатные выключения и предполагаемые паузы — разные числовые поля.
Лист «Условия» сохраняет период, календарь и применённые фильтры. Для отдельных
отчётов ноль/один выберите соответствующее кольцо и скачайте группу.

**Важно:** это анализ записей, не доказательство непрерывной работы. Журналы могут
быть неполными, а выключение могло произойти до нерабочего интервала. Устройства
без валидных событий за период, в том числе Polycom TGZ без событийного парсера,
входят в «Недостаточно данных». Предположения по паузам не прибавляются к штатным
выключениям. Новые опросы не выполняются, переимпорт прежних логов не требуется.
Прямой file:// сохраняет прежнюю сеансовую аналитику, новый срез требует runtime/БД.

Для обновления сначала дождитесь завершения импортов, записи в БД, опросов и
изменения настроек устройств. Закройте старую вкладку и Python runtime. После
остановки можно сделать резервную копию выбранной папки рабочей БД. Обновите
полный код из ветки `codex/secure-local-runtime` (Git либо ZIP), не удаляя папку
рабочей БД и исходные SR/JSON/логи. Запустите обновлённый
`START_MVP_SPHERE_SR.py`, войдите и подключите прежнюю папку БД, если она не
восстановилась автоматически. Повторно импортировать сохранённые данные не нужно.
Одного F5 недостаточно: новый Python-модуль календаря требует перезапуска runtime.

Фильтры «Домен → Тип устройства → Производитель → Модель → Локация → Адрес» содержат только значения загруженной SR с учётом вышестоящего выбора. Производитель расположен рядом с моделью. Выбор обновляет списки; расчёт аналитики запускается по «Применить». Строка текущих операций остаётся видна при переходе между модулями. В импорте обработка и запись в базу — разные этапы: 100% означает подтверждённое завершение, а не ожидание записи. Причина недоступности импорта логов и ошибки подготовки показываются непосредственно рядом с кнопкой; итог не исчезает после завершения.

Списки фильтров обновляются независимо от тяжёлых сводок и при переходе между модулями. Ошибка/ожидание списков не запрещают применять поиск и период; для списков есть отдельный повтор. Аналитика читает компактный индекс событий, а подробные доказательства — только для текущей страницы. После обновления требуется полный перезапуск Python runtime: при первом подключении существующей БД автоматически добавится аналитический индекс. Это подготовка сохранённых данных, не повторное чтение исходных файлов; БД удалять и SR/JSON/логи переимпортировать не нужно. Сначала завершите текущие опросы и сохранение. Индекс добавляет место на диске и может потребовать времени при первом запуске; затем используется для готовых запросов.

Если списки всё же недоступны, рядом показываются «Код: …» и при наличии HTTP status. Нажмите «Повторить загрузку списков»; при повторном отказе достаточно сообщить только этот код, без содержимого БД, сетевых адресов, заголовков и токенов. Списки строятся одним проходом по SR; большие записи SR не перечитываются для каждого поля. Для этой корректировки повторный импорт не нужен — используется та же сохранённая БД.

Обычная отмена старого запроса при обновлении рабочей области не должна отключать уже загруженные списки. `metadata_timeout` означает сработавший срок ожидания именно текущего запроса; `metadata_cancelled` — отмену без этого deadline. Поздние ответы и ошибки заменённых запросов не применяются к новой форме, даже если revision осталась прежней.

Импорт SR, JSON и логов показывает оценочный общий процент «≈», текущий этап, прошедшее и примерное оставшееся время. Процент обновляется по фактическим счётчикам работы/подтверждённых порций, не просто по таймеру; при записи SQLite прогресс продолжается. ETA уточняется по измеренной скорости, при недостаточной или устаревшей оценке выводится «Рассчитывается». После подтверждения записи появляется зелёное «Успешно завершено — 100%». Частичная обработка, отмена и ошибка имеют отдельные итоги; сведения об ошибках не скрываются под сообщением об успехе.

Если публикация JSON была прервана до подтверждённого завершения, последняя опубликованная версия остаётся целой, а подтверждённые партии staging доступны для продолжения. Перезапускать runtime можно только после завершения сетевых опросов и изменений настроек устройств. После контролируемого перезапуска обновлённого runtime подключите ту же рабочую БД, **не загружайте SR повторно**, выберите ту же исходную папку JSON и оставьте «Перепроверить ранее загруженные JSON» выключенным. При совпадении пути/размера/mtime/хэша префикса инструмент переиспользует подготовленные записи без повторного разбора полных файлов; изменённые/новые файлы обрабатываются. Это не разрешение обновлять код работающего runtime или удалять БД. Если JSON уже успешно опубликованы, повторять импорт не нужно.

Опросы, сбор логов, модели, авторизация и команды изменения настроек не расширены. Их план получает актуальные SR-цели из базы; запуск заблокирован во время непубликованного импорта или получения контекста. После установки версии DB-first нужен новый запуск Python runtime, а не только F5 в старой вкладке. Перед обновлением дождитесь сохранения текущей работы. Прежнюю версию не используйте для записи в уже обновлённую DB-first базу.

Общего ограничения базы в 128 МиБ нет. Ограничен размер отдельного запроса, а не история. Порции feature 060 читаются при подготовке DB-first; дальнейшие импорты добавляют нормализованные записи и публикуются транзакционно, не заменяя базу частичным состоянием браузера.

При импорте логов в локальном режиме сначала подключите рабочую папку. Каждый успешно разобранный Huawei XML сохраняет компактную контрольную точку в базе. После сбоя, закрытия браузера или остановки войдите снова и в блоке логов выберите ту же папку; кнопка «Продолжить импорт логов» использует готовые результаты без перечитывания тел неизменившихся файлов. Если была включена полная перепроверка, включите её снова. Новые и изменённые файлы читаются, префиксы сверяются. Итоговая общая аналитика публикуется только после завершения; незавершённый импорт не заменяет предыдущую версию. Сохранённые части нового импорта не исчезают из-за ошибки финальной записи.

Прогресс раздельно показывает обработанный объём, реально прочитанные байты, среднюю скорость чтения/анализа, записанные и восстановленные файлы, затем объединение событий и сохранение. Скорость не увеличивается за счёт пропущенных файлов. Реальная скорость зависит от диска и структуры журнала; на поддерживаемом браузере работают до двух Worker, на прямом index.html — один сеансовый обработчик без постоянных checkpoints. Уже запущенная старая вкладка не получает обновления задним числом: её не следует закрывать до безопасного сохранения текущих данных.

- в локальном режиме после явного выбора рабочей папки завершённые SR/JSON и компактная аналитика логов сохраняются в открытой SQLite-базе этой папки; Python runtime запоминает вне Git только путь к ней и после входа восстанавливает последнюю ревизию;
- пароли устройств, сеансовые токены, исходный `rawText` и копии полных логов в базу не записываются; прямой `file://index.html` остаётся только сеансовым;
- `localStorage`, `IndexedDB` и скрытое хранилище данных не используются;
- исходные SR/JSON не изменяются;
- готовые JSON пишутся только в явно выбранную пользователем папку;
- loopback принимает только текущий `127.0.0.1|localhost` порт, одноразовую HttpOnly-сессию и CSRF для изменений;
- сетевые обращения к оборудованию ограничены точными IP из неизменяемого плана;
- база ограничивает размер одного проверенного снимка; если её не удалось сохранить, инструмент показывает предупреждение и не заменяет прежнюю ревизию. Фактические пределы импорта зависят от диска, памяти и числа уникальных событий.

Сеансовая модель не защищает от компрометации текущей учётной записи Windows, вредоносного ПО или чтения памяти запущенного процесса.

## Справочник и развитие

Названия модулей, пользовательские статусы и справочные описания находятся в `product-catalog.js`. Общие производители, модели и статусы протоколов — в `runtime/device-catalog.json`. Новый vendor adapter допускается только после документального или проверенного на устройстве подтверждения endpoint, transport, аутентификации и схем ответов; граница регистрации находится в `mvp_runtime/polling.py`.

Node.js не является частью пользовательского запуска. Он используется разработчиком/CI только для тестов Vanilla JavaScript и проверки Справочника.

## Ключевые файлы

- `START_MVP_SPHERE_SR.py`, `mvp_runtime/` — Python 3.11+ launcher, loopback API, XLSX, polling job и Extron adapter;
- `runtime/device-catalog.json` — общий каталог устройств/протоколов;
- `index.html`, `app.js`, `styles.css`, `runtime-config.js` — интерфейс и прямой ручной режим;
- `runtime/credential-pool.js`, `vendor/xlsx.full.min.js` — проверка XLSX в браузере без CDN;
- `product-catalog.js`, `scripts/validate-reference.js` — единый Справочник и контроль согласованности;
- `python_tests/`, `tests.js` — Python API/security и интерфейсная регрессия;
- `specs/014-python-runtime-migration/`, `docs/decisions/ADR-0014-python-runtime-migration.md` — актуальное архитектурное решение.
