# ADR-0064: SQL read model вместо полной истории в браузере

**Дата:** 2026-11-19 · **Статус:** реализовано; эксплуатационная проверка реальной базы остаётся у администратора.

## Причина

Feature 060 сохраняла историю порциями, но restore по-прежнему собирал все события и JSON в память вкладки. Синхронный render вычислял все сводки до замены DOM, поэтому тяжёлая функция или исключение выглядели как неработающая навигация. Найдены также неограниченный spread и квадратичное среднее для кластеров JSON uptime. Администратор подтвердил сотни тысяч, возможность миллиона событий ВКС и рост базы; попросил DB-first для SR, JSON и логов без ухудшения опросов и writes.

## Решение

В той же явно выбранной SQLite строятся индексированные `rm_records`, метаданные подготовки, staging импортов, evidence references и pair-tombstones. Прежние порции/контрольные суммы остаются. Подготовка обрабатывает четыре порции за запрос и продолжает после сбоя; данные не перечитываются из оригинальных XML/JSON. Bootstrap передаёт только ревизию, счётчики и настройки. Миллион записей не восстанавливается в браузер.

Новый read API — POST `/api/workspace/db` с прежними admin/session/Origin/CSRF gates. Имена запросов и поля фильтров whitelisted, значения параметризованы. Страница <=100 строк, ревизия согласуется на каждом запросе. Связанные сводки, кольца, TOP, длительности и карта 7×24 считаются SQL; ответ не содержит массива всех событий. Малый LRU включает путь БД, UUID, ревизию и фильтры. Долгий запрос имеет бюджет выполнения, навигация не ждёт его синхронно. OFFSET оставлен для простого перехода страниц; для экстремально дальних страниц его стоимость остаётся техническим ограничением.

Новые импорты пишут staging, готовая версия публикуется одной транзакцией. Browser state больше нельзя использовать для полной замены БД; старые write-маршруты защищены от этого после native публикации. Для старта опроса и сбора логов временно загружается актуальный SR context и метаданные запусков, не JSON история или события. Изменение, продолжение и запуск плана блокируются, если SR ещё не опубликована/контекст не подтверждён. Vendor adapters, transport, credential lifecycle и model/identity/write gates не меняются.

XML даёт per-file compact event index в staging, не общий миллионный массив. Checkpoints из feature 060 сохраняются. JSON партии освобождают rawText и локальную историю; два соседних результата приходят по запросу, прежняя adjacent-пара удаляется через транзакционные tombstones. Поздние вставки и границы партий сохраняют прежний JS diff-контракт. Site name берётся из самого нового результата, ошибка нового не подменяется старым; exact Polycom alias сохраняется. Экспорт фактических настроек получает последние JSON только для IP выбранной таблицы.

Логи и JSON Date − Uptime можно смотреть отдельно. Длительности и срез ВКС «Учёт»/его XLSX используют только логовые доказательства, не расчётные JSON старты. Неизвестные старты не повышаются до reboot, паузы — только предположение. Для новых evidence references ведётся отдельная дедупликация; если старая проекция сохранила только 16 примеров при большем счётчике, её неполное число остаётся помеченным как минимум, а не выдумывается точная идентичность потерянных примеров.

## Проверка и ограничения

Синтетическая миграция 1 000 000 событий из 1001 прежней порции заняла около 170 секунд в финальном прогоне без XML; ответы views — от сотен байт до ~22 КиБ. Сводка ~2,2 с, TOP ~4 с после одного eligibility/join прохода, тяжёлые агрегаты ~10–12 с отдельно от потока браузера, дальняя страница ~1,4 с. Это не обещание времени на ином диске/ПК. Проверены длительности, экспорт и дальняя страница. Общего потолка базы нет, но диск, память Python/SQLite и сложность SQL остаются физическими ограничениями.

Headless Chrome проверил навигацию, питание, узкий экран, CSP, сохранность набранного фильтра при позднем ответе, сферу SR и наличие формы плана. Данные были синтетическими; реальные терминалы не вызывались. Панели обновляются отдельно от полей фильтра. Окончательный эксплуатационный тест на базе администратора обязателен.

Прямой file:// — прежний сеансовый fallback, не SQL runtime. Обновление требует нового запуска Python runtime; одно обновление вкладки старого процесса недостаточно. Старую версию нельзя использовать для записи DB-first данных. Нельзя обновлять/закрывать вкладку с неподтверждённым сохранением только ради установки новой версии.
