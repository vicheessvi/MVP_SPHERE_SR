# ADR-0044: раздельная аналитика событий логов Huawei TE

Дата: 2026-11-10. Статус: реализовано и проверено новым парсером на полном логе TE40 только в памяти; TE30/50/60 ожидают эксплуатационной проверки аналитики.

Полный XML-экспорт exact TE40 прочитан только в памяти после подтверждения модели. Обёртка `LogModule` содержит текстовые строки, но всё содержимое не является корректным XML-деревом; поэтому импорт сканирует отдельные строки ограниченной длины, не исполняя XML и не распаковывая архивы. Реальный файл, исходные строки, адрес, токены и credentials не сохранялись в репозитории.

Администратор подтвердил консервативное правило: `System start` без явного соседнего `normal ... reboot` не считается перезагрузкой. Из двух строк reboot около одного запуска строится одно событие. Только отдельный маркер `Terminal ... powered ... off` создаёт событие отключения; это не доказывает внезапную пропажу электричества. Время без зоны остаётся локальным временем терминала. События связываются лишь с единственным точным IP и актуальным deviceId SR, повторные экспорты дедуплицируются; конфликты и неподтверждённые модели не увеличивают счётчики.

Новые события живут только в памяти вкладки и отображаются в отдельных Huawei-разделах существующего модуля, не смешиваясь с `extron-reboot-v2`. Формат TE30/50/60 проверяется по каждому импортированному файлу; пользовательская проверка их реальных событий ещё требуется.

Контрольный прогон готового JavaScript-парсера на полном логе того же TE40 подтвердил распознавание трёх узких маркеров, объединение двух reboot-строк около одного запуска в одно подтверждённое событие и отдельное отключение. Исходный лог передавался только между локальными процессами в памяти и не сохранялся.

Дополнение 2026-11-10 для exact TE20: его `LogModule` содержит строки с дополнительным идентификатором потока, поэтому TE40-шаблон не переносится. Первое read-only исследование выявило `System ... boot`, но не доказало причины каждого запуска. Администратор затем сам выполнил контролируемые web-перезапуск и штатное выключение с последующим включением с пульта. В новых строках перед новым boot обнаружены соответственно `LOG_MOD_WEB` + `reboots` и отдельное `LOG_MOD_WEB` + `shut ... down ... terminal`. Только первая пара в пределах двух минут даёт подтверждённую перезагрузку; вторая запись отмечает web-команду отключения, но не аварийную потерю питания. Прочие boot остаются неизвестными, а одиночная reboot-команда не создаёт перезагрузку без последующего boot. Сырые строки, реальные временные метки, адрес и лог не сохранялись в Git; парсер TE20 отделён собственным ruleVersion.

Второй контрольный опыт 2026-11-10: администратор выбрал «Выключить» на пульте TE20 и снова включил терминал. По сравнению с исходной выборкой появился отдельный маркер `LOG_MOD_RC` с узкой фразой `user ... shut ... down ... terminal`, затем новый boot. Кнопка Power, сообщения сна и `OFFLINE` не считаются выключением. Для web и пульта производное событие содержит способ `web` или `remote_control`; оба обозначают штатную команду, но не доказывают аварийную потерю электропитания. Полный лог обрабатывался только в памяти.

Дополнение по длительным паузам: для exact TE20/30/40/50/60 после неизвестного запуска допускается отдельная низкодостоверная гипотеза «Предполагаемое отключение питания». Между соседними строками до запуска должна быть пауза не менее настраиваемого порога (начальное значение 60 минут), без явной команды reboot или штатного выключения. Пауза без нового запуска не является событием; более 30 дней отмечается как возможная аномалия часов и исключается. Время запуска не выдаётся за точное время потери питания; подтверждённые итоги не меняются. Полные журналы TE20 и TE40 использованы только в памяти для начальной проверки распределения пауз. На TE40 найден один длинный кандидат, причина которого не установлена, что подтверждает необходимость отдельной низкой достоверности. TE30/50/60 требуют эксплуатационной проверки порога.
