# ADR-0060: Guarded Answer mode для Polycom RealPresence Group

**Дата**: 2026-11-16
**Статус**: принято для exact Group 310; Group 300/500/700 предварительно до реальных write-проверок.

## Контекст

У Polycom Group два независимых пользовательских параметра Auto Answer Point-to-Point Video и Auto Answer Multipoint Video. Администратор требует управлять ими отдельно, в том числе обоими в одном плане, аналогично существующим массовым задачам Answer mode. Обычный опрос уже читает оба параметра, но write-контракт отсутствовал.

## Решение

Добавить один opt-in action ID для exact Group 300/310/500/700. План содержит две nullable цели, одно действие в плане и отдельное согласие с числом устройств. До сети проверяются актуальная SR, digest, уникальные IP и только совместимые точные модели. После существующих Polycom login/model/identity gates текущий web-bundle обязан подтвердить форму обоих полей и сохранение через `POST /rest/config` с `vars`. Pre-read принимает только `Yes`/`No`; `Do Not Disturb` и неизвестные коды блокируют write. Один запрос содержит только изменяемые поля (одно или два), ответ требует точного `NOERROR` на каждое. Оба поля перечитываются до двух последовательных совпадений целевой пары в ограниченное время. Неясный результат не повторяет write автоматически. HTTPS-сертификат проверяется по умолчанию; исключение — только по явному разрешению текущего запуска. Никакого HTTP fallback.

## Доказательства и ограничения

На exact Group 310 текущий web-bundle показал `generateWriteJsonData`, `processJsonWriteValue`, `setConfiguration` и проверку `NOERROR`. Контролируемые одиночные и парные переходы с отдельными разрешениями вернули точные ответы и совпали с web-меню; исходное `Yes/No` восстановлено. Один ранний post-read оказался переходным, что потребовало устойчивой повторной проверки чтением. Эти наблюдения не доказывают write-совместимость любой прошивки Group 300/500/700; их статус остаётся предварительным. Group 300 с прежней HTTP-only прошивкой по-прежнему не получает credentials по HTTP.

## Последствия

Обычный JSON-опрос и сбор логов остаются read-only; при отсутствии action ID код записи недостижим. Структура результата сохраняет безопасные исходную и конечную пару, статус и причину отказа без credentials, cookie или сырых ответов. Исторические JSON не переписываются.
