# ADR-0068 — файловые ошибки при полной перепроверке логов

Дата: 2026-11-24. Статус: принято; исправление дефектов без изменения constitution.

Актуализация 2026-11-25 / ADR-0070: требование XML EOF ниже больше не отбрасывает
известный полностью прочитанный LogModule. Он разбирается как fragment с явной
provenance/quality, без отрицательных выводов по одним фрагментам. Настоящий
read/short IO failure старых доказательств по-прежнему не превращается в успех.

## Основание

После обновления правил пользователь повторно получал log_recheck_incomplete на
одном месте. Guard прерывал всю папку на любом старом unmatched/error пути, даже
если файл ранее содержал только metadata. Сообщение не называло файл и причину.
Отдельно воспроизведён ложный incomplete_log у закрытого XML с длинным whitespace
после LogModule. Пользовательская папка на этом ПК недоступна, поэтому точная
причина её конкретного файла не объявляется подтверждённой.

## Решение

Проверять остальные файлы, сохранять успешные scans прежними versioned checkpoints
и staging. Файловые ошибки — только безопасные path/reason/size/blocking metadata;
отчёт <=100, блокирующие пути приоритетны независимо от порядка. После аварии
Worker следующий файл получает новый Worker, максимум две активные линии. Тот же
файл не перечитывается автоматически в рамках попытки. DB/checkpoint failure и
cancel не превращаются в файловое предупреждение.

Прежнюю аналитику защищает отдельный predicate: digest/analysisComplete=true и
неизвестная legacy запись известного аналитического формата консервативны;
явные metadata/parse failure без доказательств не блокируют. При настоящем отказе
повторного чтения прежних доказательств после всей папки atomic finish не вызывается.
Опубликованная ревизия остаётся активной, готовые scans используются при повторном
выборе папки. Нельзя выдавать повреждённый файл за успешно проверенный или молча
удалять его события. Если заблокированных доказательств нет, полный завершённый
результат публикуется с явными предупреждениями качества. Новая ошибочная запись
получает analysisComplete=false, не фиктивную успешную ruleVersion; bootstrap не
выводит её как повод для бесконечного обновления правил.

XML completeness-tail остаётся bounded (512/2048), длинный пробельный suffix
сворачивается с сохранением одного разделителя. Это не склеивает разорванные
токены на границе chunks. Отсутствующий closing tag/посторонний trailer не принят.
Event grammar, классификация, source/IP/model gates и версии правил прежние;
успешные текущие checkpoints совместимы. Исходные файлы не правятся.

Файловой ошибкой/отменой до finish заканчивается активная UI-операция, а не
публикация. Снимается только UI lock от этого неопубликованного log staging,
чтобы план по уже опубликованной SR оставался доступен. Неполная SR, DB conflict
или неизвестный исход записи не получают такого исключения. История не
восстанавливается в браузер, replacement-save не применяется.

## Проверка

Синтетические metadata/старый parse-error/реальный read failure/неподдерживаемая
замена; все последующие файлы проверены; resume читает только неготовый файл.
Проверены Worker crash, приоритет/предел отчёта, XML padding более 1 МиБ, реальная
обрезка и некорректный тег с whitespace на границе chunks. Real Python/SQLite/
browser подтверждает прежнюю ревизию и доступность плана после ошибки, refresh,
восстановление файла, только одно повторное body-read и отсутствие нового loop.
Реальные логи, устройства и credentials не использовались.
