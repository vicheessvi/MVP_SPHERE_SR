# Feature Specification: SR inventory, polling history and analytics

**Feature Branch**: `not-created`
**Created**: 2026-08-09
**Status**: Ready for planning
**Input**: Развитие MVP_SPHERE_SR в локальный инструмент инвентаризации, импорта результатов опросов, истории, аналитики и подготовки расширяемого polling-контура для ВКС-терминалов, контроллеров и панелей управления.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Импортировать SR и получить inventory (Priority: P1)

Администратор МЦТП загружает локальную XLSX-выгрузку SR и получает актуальный inventory, разделённый на терминалы ВКС, контроллеры и панели управления. Исходные значения сохраняются, а неполные строки не останавливают импорт остальных записей.

**Why this priority**: SR является источником локаций и оборудования; без inventory невозможно надёжно сопоставлять результаты опросов и строить аналитику.

**Independent Test**: Загрузить синтетическую XLSX с тремя категориями оборудования, строкой без домена и строкой с некорректным IP; убедиться, что корректные устройства отображаются в нужных категориях, домен остаётся optional, а проблема строки зафиксирована отдельно.

**Acceptance Scenarios**:

1. **Given** синтетическая SR с обязательными колонками, **When** пользователь импортирует XLSX, **Then** создаётся запись импорта и inventory с исходными значениями строк.
2. **Given** SR без колонки «Домен», **When** выполняется импорт, **Then** импорт завершается, а домен устройств имеет пустое значение.
3. **Given** строки `Тип модели = Video Conference`, `Тип оборудования = controller` и `Тип модели = Панель управления`, **When** строится inventory, **Then** строки классифицируются как ВКС-терминал, контроллер и панель соответственно.
4. **Given** повторная SR, **When** совпадают inventory/serial либо другие доступные устойчивые идентификаторы, **Then** устройство обновляется без потери истории; новые добавляются, отсутствующие помечаются как отсутствующие в актуальной SR.

### User Story 2 - Импортировать результаты запусков и увидеть историю (Priority: P2)

Администратор выбирает локальные JSON-файлы из папки запуска, а система определяет timestamp запуска, IP из имени файла, классификацию Extron по содержимому и связывает результат с inventory. Каждый результат сохраняется как отдельный snapshot устройства и не затирает историю.

**Why this priority**: Это рабочий end-to-end путь от inventory к наблюдаемому состоянию оборудования без выдумывания неизвестного polling API.

**Independent Test**: После импорта SR загрузить два синтетических запуска для одного IP и один файл неизвестного IP; убедиться, что устройство имеет два snapshots, изменения рассчитаны, а неизвестный IP сохранён как unmatched.

**Acceptance Scenarios**:

1. **Given** файл `10.10.20.30.json`, **When** IP существует в SR, **Then** polling result связывается с соответствующим устройством.
2. **Given** Extron JSON с `Controller Type = Primary Controller`, **When** SR описывает контроллер, **Then** результат классифицируется как controller без конфликта.
3. **Given** Extron JSON с `Controller Type = TLP`, **When** SR описывает панель, **Then** результат классифицируется как panel без использования термина «контроллер» в UI.
4. **Given** конфликт классификации SR и JSON, **When** выполняется импорт, **Then** snapshot сохраняется и получает диагностический конфликт.
5. **Given** malformed, пустой, неизвестный или unmatched JSON среди корректных файлов, **When** выполняется batch import, **Then** ошибка фиксируется для конкретного файла, остальные файлы продолжают обрабатываться.
6. **Given** повторный импорт одинаковых bytes того же запуска, **When** выполняется импорт, **Then** дубликат не создаёт новый snapshot.

### User Story 3 - Анализировать категории оборудования (Priority: P3)

Администратор открывает модули «Терминалы ВКС», «Контроллеры» и «Панели управления», видит весь inventory соответствующей категории независимо от наличия истории, фильтрует таблицу и открывает карточку устройства с последним состоянием, историей и изменениями.

**Why this priority**: Категорийные экраны являются основным рабочим инструментом инвентаризации и диагностики.

**Independent Test**: На синтетическом inventory открыть каждый модуль, применить фильтры по SR и аналитическим полям, затем открыть устройство без опросов и устройство с двумя snapshots.

**Acceptance Scenarios**:

1. **Given** inventory с разными производителями, **When** открыт категорийный модуль, **Then** отображаются все устройства категории, включая неподдерживаемые для polling и ни разу не опрошенные.
2. **Given** устройство с историей, **When** открыта его карточка, **Then** видны последний и предыдущий опрос, статусы и список изменений old/new.
3. **Given** устройство без history, **When** открыта карточка, **Then** показано явное состояние «не опрошено» без фиктивных данных.
4. **Given** фильтры по SR и доступной аналитике, **When** пользователь применяет их, **Then** таблица показывает только соответствующие устройства и позволяет сбросить фильтры.

### User Story 4 - Получить достоверный главный дашборд (Priority: P4)

Администратор открывает главный экран «Дашборд» и видит агрегаты, вычисленные только по загруженной SR и фактическим polling results, с возможностью перейти к проблемным устройствам.

**Why this priority**: Дашборд ускоряет оценку состояния, но его показатели имеют смысл только после появления inventory и history.

**Independent Test**: Импортировать синтетические данные с опрошенными, неопрошенными, успешными, ошибочными и ping-failed устройствами; сверить агрегаты с исходными записями.

**Acceptance Scenarios**:

1. **Given** inventory трёх категорий, **When** открыт дашборд, **Then** показаны общее число и число по категориям.
2. **Given** устройства с разной polling history, **When** открыт дашборд, **Then** корректно показаны опрошенные, неопрошенные, успешные, ошибочные, ping failures и устройства с изменениями.
3. **Given** отсутствие надёжного признака authorization, reboot или GCPlus, **When** открыт дашборд, **Then** такие метрики помечены как недоступные, а не заполняются эвристикой или demo-значением.

---

### User Story 5 - Подготовить безопасный polling run (Priority: P5)

Администратор выбирает категорию и фильтры устройств, видит состав будущего запуска, дату/время и поддержку adapters. Запуск сетевого опроса разрешён только при наличии реального adapter; отсутствие protocol/auth не имитируется.

**Why this priority**: Управление polling необходимо продукту, но достоверный транспорт нельзя реализовать без документированного протокола и схемы авторизации.

**Independent Test**: Создать план запуска для Extron и неподдерживаемого производителя; убедиться, что состав и support status видны, credentials не сохраняются, а сетевой запуск недоступен без adapter.

**Acceptance Scenarios**:

1. **Given** выбранные фильтры, **When** пользователь формирует запуск, **Then** система показывает категорию, список и количество устройств, дату/время и support status.
2. **Given** отсутствующий polling adapter, **When** пользователь пытается начать опрос, **Then** сетевой запрос не выполняется и UI явно сообщает `not implemented`.
3. **Given** будущий adapter, **When** он регистрируется для пары category/manufacturer, **Then** общий inventory/history/analytics pipeline не требует изменения.

### Edge Cases

- XLSX отсутствует, повреждён, имеет неизвестный лист, повторяющиеся заголовки или неполный набор обязательных колонок.
- IP представлен строкой с пробелами, пуст, невалиден, повторяется в SR либо изменился между импортами.
- В строке отсутствуют manufacturer/model или встречается alias `Huawey`; исходное значение сохраняется, нормализованный alias используется только для сопоставления.
- Имя папки запуска не соответствует `YYYY-MM-DD_HH-MM-SS` либо timestamp календарно невалиден.
- Имя JSON не является корректным IPv4, JSON пуст/повреждён или не содержит ожидаемой структуры.
- `Controller Type` отсутствует, неизвестен либо конфликтует с категорией SR.
- Batch содержит одновременно корректные, неподдерживаемые, unmatched и ошибочные файлы.
- Новая SR больше не содержит устройство, у которого есть polling history.
- Одинаковые bytes импортируются повторно под тем же или другим именем.
- Список ignored/volatile fields пуст либо содержит некорректные пути.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST импортировать локальный XLSX SR без передачи содержимого во внешние сервисы.
- **FR-002**: Импорт MUST поддерживать обязательные колонки: «Название комнаты», «Адрес комнаты», «VIP комната», «Тип оборудования», «Наименование», «Модель», «Тип модели», «Производитель», «IP», «MAC», «SIP URI», «Инвентарный номер», «Серийный номер», «VIP оборудование».
- **FR-003**: Колонка «Домен» MUST быть optional; её отсутствие не должно блокировать импорт.
- **FR-004**: Система MUST сохранять исходные значения SR отдельно от нормализованных значений.
- **FR-005**: IP MUST нормализоваться безопасно; пустые и невалидные значения MUST становиться проблемами конкретной строки, а не ошибкой всего импорта.
- **FR-006**: Устройства MUST классифицироваться по правилам: `Тип модели = Video Conference`, `Тип оборудования = controller`, `Тип модели = Панель управления`, с нормализацией регистра/пробелов без изменения raw.
- **FR-007**: Inventory MUST включать все manufacturers/models из SR, а известные списки MUST использоваться только для support/adapter metadata.
- **FR-008**: Alias manufacturer `Huawey` MAY нормализоваться к Huawei для сопоставления, при этом raw manufacturer MUST сохраняться.
- **FR-009**: Повторный импорт SR MUST обновлять совпавшие устройства, добавлять новые и помечать отсутствующие в актуальной SR без удаления polling history.
- **FR-010**: При идентификации MUST приоритизироваться inventory number и serial number; IP не должен быть единственным устойчивым идентификатором при наличии более сильного значения.
- **FR-011**: Система MUST импортировать несколько локальных JSON polling results независимо, не прекращая batch из-за одного файла.
- **FR-012**: Timestamp запуска MUST безопасно извлекаться из `YYYY-MM-DD_HH-MM-SS`; невалидное имя MUST фиксироваться как проблема запуска.
- **FR-013**: IP polling result MUST извлекаться из имени JSON, нормализоваться и сопоставляться с актуальным/историческим inventory.
- **FR-014**: Unmatched result MUST сохраняться без потери raw evidence и иметь явный статус.
- **FR-015**: Extron result MUST дополнительно классифицироваться по `Controller Type`: `Primary Controller` → controller, `TLP` → panel.
- **FR-016**: Конфликт категории SR и JSON MUST сохраняться как диагностическое состояние без потери result.
- **FR-017**: Device и PollingResult MUST быть разными сущностями; один Device MUST иметь множество PollingResults.
- **FR-018**: PollingResult MUST сохранять raw evidence/hash, run timestamp, import timestamp, filename, matching status, normalized status и issues.
- **FR-019**: Дубликаты MUST определяться по содержимому и контексту запуска, а повторный импорт MUST быть идемпотентным.
- **FR-020**: Последовательные results одного устройства MUST формировать историю и change events с временем, field path, old value, new value и ссылками на оба snapshots.
- **FR-021**: Список ignored/volatile fields MUST быть конфигурируемым; неизвестные поля не должны игнорироваться автоматически.
- **FR-022**: Extron ping failure MUST определяться только при надёжном сочетании `failedStage = ping` и `ping.ok = false`, устойчивом к регистру имени блока и отсутствующим полям.
- **FR-023**: Authorization error, reboot и GCPlus MUST иметь отдельные normalized analytics states; без надёжного признака они MUST оставаться `unknown/not available`.
- **FR-024**: Навигация MUST содержать «Дашборд», «Терминалы ВКС», «Контроллеры» и «Панели управления».
- **FR-025**: Каждый категорийный модуль MUST показывать весь соответствующий SR inventory независимо от наличия polling history.
- **FR-026**: Категорийные таблицы MUST фильтроваться по доступным SR-полям и доступным аналитическим статусам.
- **FR-027**: Карточка устройства MUST показывать SR context, polling support, последнее состояние, историю и изменения.
- **FR-028**: Дашборд MUST агрегировать только вычислимые фактические показатели по трём категориям и предоставлять drill-down к отфильтрованным устройствам.
- **FR-029**: Система MUST отличать `supported`, `unsupported/not implemented` и неизвестную polling capability.
- **FR-030**: Архитектура polling MUST разделять category, manufacturer, model, transport/API adapter и normalization.
- **FR-031**: UI подготовки run MUST показывать тип, фильтры, выбранное количество и список устройств, дату/время и status выполнения/поддержки.
- **FR-032**: Без зарегистрированного реального adapter система MUST NOT выполнять фиктивные сетевые запросы.
- **FR-033**: Device credentials MUST NOT храниться в source code, Git, frontend/application logs, polling result или открытом UI.
- **FR-034**: Локальные SR, polling JSON, run folders, database/state exports и secrets MUST быть исключены из Git.
- **FR-035**: Система MUST использовать существующую demo-auth infrastructure без добавления отдельного RBAC/ACL framework; пользовательская роль отображается как «Администратор МЦТП».
- **FR-036**: Malformed JSON, empty JSON, missing/unknown IP, unknown manufacturer/model, missing/conflicting Controller Type и unknown structure MUST фиксироваться на уровне файла/result.
- **FR-037**: Backup/restore MUST включать новые inventory/history/analytics сущности без активной login-сессии и без credentials.
- **FR-038**: Существующая project/snapshot/change функциональность MUST оставаться доступной либо совместимо мигрироваться без потери данных.

### Key Entities

- **SRImport**: Факт локального импорта SR, hash/имя/время, заголовки, качество и ссылка на актуальность inventory.
- **Location**: Локация из SR с названием, адресом, VIP и optional domain.
- **Device**: Устойчивая inventory-сущность с raw/normalized SR metadata, category, identifiers, manufacturer/model, актуальностью и polling capability.
- **PollingAdapterDescriptor**: Метаданные поддержки пары category/manufacturer/model без credentials и без фиктивного транспорта.
- **PollingRun**: План или импортированный запуск с timestamp, источником, selection summary и агрегированным статусом.
- **PollingResult**: Неизменяемый snapshot одного устройства/файла внутри запуска с raw hash, match/classification, normalized status и issues.
- **DeviceChange**: Объяснимое изменение между двумя последовательными PollingResults одного Device.
- **InventoryIssue**: Ошибка строки SR, несовпадение IP, classification conflict или проблема входного файла.
- **AnalyticsProjection**: Вычисляемые агрегаты по inventory и latest results, не являющиеся отдельным источником истины.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь импортирует валидную синтетическую SR до 1 000 строк и видит inventory по трём категориям не более чем за 10 секунд в согласованном desktop browser.
- **SC-002**: Отсутствие optional-колонки «Домен» и наличие одной некорректной строки не препятствуют импорту остальных корректных строк.
- **SC-003**: В контрольном наборе 100% строк с тремя заданными правилами категорий попадают в ожидаемые модули без изменения raw значений.
- **SC-004**: Batch с одним malformed JSON и девятью валидными JSON сохраняет результаты всех девяти валидных файлов и отдельную ошибку malformed файла.
- **SC-005**: Повторный импорт одинаковых bytes не увеличивает число PollingResults.
- **SC-006**: После двух разных results одного Device пользователь видит оба snapshots и все обнаруженные изменения с old/new и двумя источниками.
- **SC-007**: Dashboard totals для synthetic fixture полностью совпадают с ручным подсчётом inventory/latest results.
- **SC-008**: Ни один unsupported manufacturer не отображается как доступный для API polling.
- **SC-009**: Автоматические проверки покрывают не менее 14 обязательных сценариев из задания и весь ранее существовавший regression suite остаётся успешным.
- **SC-010**: Поиск в отслеживаемых файлах не обнаруживает SR XLSX, реальные run folders, локальную production state/database или device credentials.

## Assumptions

- Первый безопасный вертикальный срез сохраняет direct-open local application и выполняет только локальные imports; реальный сетевой polling блокирован до предоставления документированного protocol/auth и примеров.
- Extron JSON fixtures текущего проекта достаточны для `Controller Type`, базовой normalization/change detection и ping failure, но недостаточны для authorization/reboot/GCPlus.
- XLSX имеет хотя бы один лист; по умолчанию импортируется первый непустой лист с ожидаемыми заголовками.
- Для нового inventory нет искусственного product-level retention limit; фактическая browser storage quota остаётся ограничением текущего demo runtime и должна быть явно показана.
- Raw SR XLSX не сохраняется целиком в persistent state; сохраняются hash/import metadata и строки inventory, необходимые для локальной работы.
- Реальные credentials не входят в feature; будущий polling adapter должен получать их только из локального transient/OS-backed механизма, который будет определён отдельным ADR.
- Existing project/snapshot entities сохраняются для обратной совместимости, а новый device-centric inventory/history добавляется рядом с ними.
- Полноценное расписание в закрытой вкладке невозможно в browser-only runtime; UI хранит план запуска, но не заявляет фоновое выполнение.
