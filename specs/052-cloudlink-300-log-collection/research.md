# Research: экспорт логов CloudLink 300

## Подтверждено в проекте

- Существующая опция `collectLogs` уже отделена от `collectJson`; browser выбирает папку логов, создаёт timestamp-папку, пишет поток и подтверждает сохранение. `PollingJob` держит поток только до ACK, не создаёт серверный spool.
- Текущий импорт показывает метаданные XML и точное сопоставление IP, не исполняет содержимое; событийная аналитика Bar/Box 300 не подтверждена.
- Адаптер `huawei_300.py` уже выполняет до credentials exact numeric pre-auth model и после входа exact модель плюс SN/MAC. Это обязательная граница любого нового экспорта.
- Обычная проверка HTTPS-сертификата подключённого Bar 300 не прошла; администратор отдельно разрешил принять его самоподписанный сертификат только для текущей read-only проверки. Production TLS-policy по умолчанию не ослабляется.
- [Официальная инструкция Huawei](https://support.huaweicloud.com/intl/en-us/meeting_faq/equip_log.html) описывает пользовательский экспорт через «Maintenance → Logs» и отдельную «Maintenance → Diagnostics → One-Click Diagnostics». Она не указывает приватный URL, MIME или формат файла; эти сведения не подменяются догадкой.

## Подтверждённый экспорт Bar 300

- Текущий bundle exact Bar 300 содержит связку кнопки `ExportLogBtn.onClick=i.handleExportLogData` и `handleExportLogData=function(){window.open("log?rmd="+Math.random()...}`. Это отдельный GET `/log?rmd=<nonce>` по HTTPS/443, не TE token URL и не REST экспорт серии 310. Соседние действия очистки логов и HID-диагностики не используются.
- После pre-auth numeric model 18, авторизации и post-auth точной модели с устойчивой идентичностью контрольное чтение заголовков и первых 4096 байт вернуло HTTP 200, `application/x-octet-stream`, XML-префикс `<?xml` с `<LogModule`. `Content-Length` отсутствовал. Затем проверенный потоковый opener прочитал весь ответ порциями без сохранения файла и вывода строк: получен закрывающий `</LogModule>`. Журнал был крупным, что подтверждает необходимость потоковой передачи. Это проверка чтения, а не подтверждение пользовательского сохранения в выбранную папку.
- Выгрузка использует cookie текущей web-сессии и не помещает CSRF/пароль в URL. Query `rmd` — только cache-busting nonce.
- После интеграции администратор подтвердил успешное формирование опросов и логов на Bar 300, Box 300 и Box 600. Это пользовательская эксплуатационная проверка файлов, не отдельная проверка агента каждого Box и не подтверждение событийного разбора. Точные model/identity gates и маркеры bundle остаются обязательными.

## Решение

Добавлен один потоковый read-only opener без буферизации полного лога, с проверкой HTTP/MIME/XML-префикса и передачей только в существующий `on_log`. Box 300/600 используются условно при собственной exact модели, идентичности и двух текущих bundle-маркерах; после подтверждения администратором новых запусков все три модели получают `logCollection.validationStatus=confirmed_user_validation`. Исторические предварительные файлы не переписывать. При drift — `protocol_required`, без угадывания URI. Событийная аналитика `LogModule` для серии 300 остаётся отдельной задачей.
