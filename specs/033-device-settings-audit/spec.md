# Feature Specification: Сверка настроек терминалов ВКС

**Feature Branch**: `codex/secure-local-runtime`
**Created**: 2026-10-28
**Status**: Draft — способ безопасного задания пароля и схема входной таблицы требуют уточнения
**Input**: Расширить задачу контроля HTTP/Telnet до анализа настроек из загруженных файлов опроса, дополнения исходной таблицы фактическими значениями, локального XLSX-отчёта и последующего модельного опроса/управления.

## User Scenarios & Testing

### User Story 1 — Сверка с уже полученными опросами (Priority: P1)

Администратор загружает список устройств и общую папку результатов опросов. Инструмент связывает каждую строку списка с соответствующим устройством и последним пригодным результатом, показывает фактические настройки и позволяет скачать дополненную таблицу XLSX. Существующие столбцы и их значения сохраняются.

**Why this priority**: Отчёт по уже имеющимся данным даёт пользу без изменения устройств и позволяет увидеть, каких сведений не хватает для дальнейшего опроса.

**Independent Test**: Загрузить синтетический список и папку с успешными, ошибочными, неполными и конфликтными файлами; сравнить строки отчёта с источниками.

**Acceptance Scenarios**:

1. Given одна однозначная строка устройства и подтверждённый последний JSON, when администратор формирует отчёт, then факт берётся из этого JSON, исходные значения таблицы остаются неизменными, а рядом с заявленными настройками добавлены фактические значения.
2. Given отсутствующий, устаревший, неподдерживаемый или конфликтный результат, when строится отчёт, then факт явно неизвестен и не подменяется утверждением об отключении протокола.
3. Given значения в столбцах «Локальная камера» и «Работы проведены», when формируется отчёт, then они сохраняются как есть и не влияют на оценку остальных параметров.

---

### User Story 2 — Дополнительные параметры в новых опросах (Priority: P1)

Администратор запускает обычный read-only опрос точной модели терминала. JSON дополнительно содержит источник и фактическое состояние Telnet, HTTP, SNMP v2, автоматического обновления, автоответа, NTP и его серверов, Wi-Fi, SSH и управления питанием там, где чтение подтверждено для конкретной модели и прошивки.

**Why this priority**: Отчёт должен со временем получать факты с самого устройства, а не только значения из таблицы или догадки по названию настройки.

**Independent Test**: Для каждого подтверждённого модельного контракта сопоставить контрольный ответ устройства и JSON, затем проверить неизвестное/непредоставленное значение и отсутствие побочных изменений.

**Acceptance Scenarios**:

1. Given подтверждённый read-only контракт поля для точной модели, when устройство опрошено, then JSON содержит фактическое значение, источник, время и статус чтения без учётных данных.
2. Given только путь к настройке в интерфейсе либо отсутствие параметра в модели, when устройство опрошено, then JSON сообщает «не подтверждено» или «не предоставлено»; отсутствие меню не трактуется как выключенный TCP-порт.

---

### User Story 3 — Защищённый запуск плана (Priority: P1)

Администратор получает доступ к созданию и запуску плана только после отдельной проверки права доступа. Учётные данные для входа в инструмент не смешиваются с учётными данными устройств, не попадают в таблицу, JSON, аналитику или внешний сервис.

**Why this priority**: Задача может читать чувствительные настройки и в будущем менять их, поэтому обход защиты доступа недопустим.

**Independent Test**: Проверить отказ до авторизации, допуск администратора, завершение сеанса и отсутствие секрета в клиентских файлах, отчётах и логах.

**Acceptance Scenarios**:

1. Given нет действительного административного сеанса, when пользователь открывает план, then запуск опроса и управленческих задач недоступен.
2. Given авторизованный администратор, when он завершает сеанс, then доступ и временные учётные данные удаляются.

---

### User Story 4 — Возможность изменения параметров (Priority: P2)

Администратор может отдельно выбрать подтверждённую для конкретной модели задачу изменения настройки. Каждая запись требует явного согласия, проверки устройства до действия и повторного чтения значения после него; задача не запускается как побочный эффект обычного опроса.

**Why this priority**: Ошибочная массовая запись может нарушить управление терминалами и связь с ними.

**Independent Test**: На синтетических и отдельно согласованных реальных устройствах проверить отказ при расхождении модели, неизвестном контракте, неполном ответе и неподтверждённом результате записи.

**Acceptance Scenarios**:

1. Given нет отдельного разрешения на изменение, when запускается обычный опрос, then устройство не получает команд изменения.
2. Given подтверждённый модельный write-контракт и явное разрешение, when изменение сделано, then успех фиксируется только после повторного чтения целевого значения.

### Edge Cases

- Один IP соответствует нескольким устройствам, имя файла расходится с IP в JSON или устройство сменило идентичность: автоматическая сверка блокируется.
- Новый файл опроса ошибочен или не содержит поле: старое значение не выдаётся за актуальный факт.
- «Telnet отсутствует» и «SNMP v2 отсутствует» означают отсутствие подтверждённой настройки, а не доказанно закрытый сетевой порт.
- В NTP нужно различать включение синхронизации, автоматический/ручной выбор и один либо несколько адресов серверов.
- «Автодозвон» в исходной таблице трактуется как указанная администратором настройка автоматического ответа, а не запуск исходящего вызова.
- Путь к меню «Cloud platform type» сам по себе не доказывает, что он управляет автоматическим обновлением ПО; до подтверждения семантики факт остаётся неизвестным.
- Отсутствие Wi-Fi в меню модели или прошивки не приравнивается к отключённому Wi-Fi.
- Путь «Hung-up Button Long Press» не приравнивается автоматически к отключению спящего режима без проверки значения и смысла настройки.

## Requirements

### Functional Requirements

- **FR-001**: Инструмент MUST принимать список устройств в формате XLSX с исходными колонками SR и добавленными администратором настройками, сохраняя все исходные строки и порядок колонок.
- **FR-002**: Инструмент MUST дополнять отчёт фактическими значениями `Telnet, факт` и `HTTP, факт` сразу после единой колонки `Telnet/HTTP`, а также `SNMP v2, факт`, `Автообновление, факт`, `Автодозвон, факт`, `NTP, факт` и `Wi-Fi, факт` сразу после одноимённых колонок. Подтверждённый шаблон «Терминалы ВКС» содержит 47 заголовков, 1 строку заголовков и ни одной строки устройства. Для HTTP и Telnet пользователь подтвердил допустимые значения «Включено»/«Отключено»; формат записи двух ожиданий внутри одной ячейки `Telnet/HTTP` и значения остальных колонок остаются TBD до заполненного обезличенного примера.
- **FR-003**: Значения «Локальная камера» и «Работы проведены» MUST сохраняться без проверки и без влияния на оценку остальных полей.
- **FR-004**: Сопоставление строки списка и JSON MUST использовать однозначную идентичность, точный IP имени файла и внутри JSON, точную модель и ключ подтверждённого адаптера; неоднозначность MUST давать явный неизвестный статус.
- **FR-005**: Для каждого факта MUST сохраняться модель, исходный путь поля JSON, время опроса и статус доступности. Пустое или неподдерживаемое значение MUST NOT считаться отключённым.
- **FR-006**: Новые опросы MUST собирать только модельно подтверждённые поля read-only. Путь к настройке в web-меню не считается доказательством сетевого API или формата ответа.
- **FR-007**: Терминалы Huawei TE20/30/40/50/60, CloudLink Bar 300/310, Box 300/310/600/610 и Polycom RealPresence Group 300/310/500/700 MUST иметь отдельную матрицу полей, доступности и статуса проверки.
- **FR-008**: Новые JSON MUST содержать подтверждённые фактические состояния SSH и управления питанием помимо полей отчёта; если они не прочитаны, JSON MUST хранить явный неизвестный/непредоставленный статус.
- **FR-009**: Обычный опрос MUST ограничиваться чтением. Изменение параметров, включая открытие HTTP/Telnet, MUST быть отдельной явно запрошенной операцией, никогда не побочным эффектом чтения. Для каждого сочетания модели, параметра и целевого значения нужна подтверждённая машинная схема, разрешение администратора, pre-write проверка идентичности и post-read; пока такие контракты не получены, новое изменение MUST оставаться `protocol_required` и не отправлять команду устройству. Уже существующая opt-in задача закрытия портов сохраняется.
- **FR-010**: При первом запуске на каждом ПК администратор MUST задать логин и пароль в интерфейсе; последующие запуски MUST требовать входа. Python runtime MUST проверять доступ до приёма учётных данных оборудования и любых polling job API. В профиле Windows вне Git MAY храниться только версионированное salted scrypt-проверочное значение, не открытый пароль. Выход MUST закрывать доступ и очищать временные пары устройств; прямой `index.html` не получает сетевой опрос. Повторная первичная настройка при существующем проверочном файле запрещена.
- **FR-011**: Отчёт XLSX MUST формироваться локально, сохранять исходные значения и не содержать секретов или формул из недоверенных строк.
- **FR-012**: Существующие ручной импорт, подтверждённые опросы и отдельная opt-in задача закрытия HTTP/Telnet MUST сохраняться до согласованной замены; новое чтение не должно автоматически менять настройки.

### Key Entities

- **Строка плана работ**: исходные сведения SR, желаемые значения настроек и две непроверяемые служебные колонки.
- **Результат опроса**: точное устройство, время, подтверждённые поля и статусы доступности с указанием источников.
- **Фактическая настройка**: модельный параметр, исходное значение, интерпретация только после evidence review, доказательство и уверенность.
- **Отчёт сверки**: копия исходной таблицы с добавленными фактическими колонками и явными пробелами данных.
- **Административный сеанс**: временное право сформировать и запустить план, отдельно от учётных данных устройств.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% строк принятого XLSX присутствуют в скачанном отчёте в прежнем порядке; «Локальная камера» и «Работы проведены» неизменны.
- **SC-002**: 100% заполненных фактических значений отчёта имеют один однозначно связанный файл опроса и указанный источник поля; конфликт и отсутствие данных никогда не выдаются как «отключено».
- **SC-003**: В контрольной матрице каждого подтверждённого модельного поля фактический JSON совпадает с устройством; непроверенные модели или firmware-ветки остаются помеченными для проверки.
- **SC-004**: Любой запуск записи без отдельного подтверждения блокируется; успех подтверждённого изменения проверяется повторным чтением в 100% контрольных тестов.
- **SC-005**: В исходном коде, отчёте XLSX, JSON, аналитике и логах нет открытых паролей; сетевые обращения остаются в пределах явно выбранных адресов устройств и локального runtime.

## Assumptions

- Администратор предоставил проверенные им пути меню. Они описывают местоположение параметров для человека, но не URL, команды или структуру машинного ответа.
- В файле-списке могут быть сохранены дополнительные колонки помимо схемы SR; они не являются устройствами SR и не включаются в общий инвентарь.
- Конкретные поля и статусы формируются только после изучения обезличенных примеров XLSX/JSON либо контролируемого read-only запроса к точной модели.
- Новые write-операции не выполняются до отдельного evidence review; локальный verifier реализуется отдельно от паролей оборудования и не ослабляет одноразовую loopback-сессию.
