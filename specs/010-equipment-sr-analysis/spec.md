# Feature Specification: Оборудование, время опроса и масштабируемый SR

**Feature Branch**: `010-equipment-sr-analysis`

**Created**: 2026-08-12

**Status**: Approved for implementation

**Input**: Объединить семь категорий в модуль «Оборудование», добавить четыре SR-категории, перейти к достоверно маркированному времени файла, разделить пользовательские статусы, ограничить change detection значимыми параметрами и оптимизировать импорт SR.

## User Scenarios & Testing

### User Story 1 - Работать с единым модулем оборудования (Priority: P1)

Администратор МЦТП раскрывает пункт «Оборудование», выбирает одну из семи категорий и видит общий inventory-интерфейс с понятным активным разделом.

**Why this priority**: Новая структура навигации и четыре категории являются основой дальнейших опросов и аналитики.

**Independent Test**: Импортировать синтетическую SR с семью типами, раскрыть меню и убедиться, что каждая строка находится ровно в ожидаемой категории, включая устройства без результатов опроса.

**Acceptance Scenarios**:

1. **Given** загружена SR с семью утверждёнными типами, **When** раскрыт пункт «Оборудование», **Then** видны «Терминалы ВКС», «Контроллеры», «Панели управления», «Коммутаторы», «Матричные коммутаторы», «Скалеры» и «Аудио процессоры».
2. **Given** выбран дочерний модуль, **When** пользователь просматривает навигацию, **Then** родитель и выбранная категория визуально различимы.
3. **Given** SR-строка нового типа без polling history, **When** открыт её модуль, **Then** устройство присутствует в общей таблице, фильтрах и карточке без фиктивного результата.
4. **Given** неизвестный тип или различия регистра/пробелов, **When** строка классифицируется, **Then** утверждённые значения нормализуются однозначно, неизвестное остаётся `other`, а устройство не попадает сразу в несколько категорий.

---

### User Story 2 - Видеть достоверное время и состояние опроса (Priority: P1)

Администратор видит «Дата и время опроса» и статус, соответствующие фактически доступным доказательствам конкретного файла, без подмены времени папки датой результата или общей ошибки ошибкой авторизации.

**Why this priority**: Ошибочная хронология и неверная причина сбоя делают историю и Dashboard недостоверными.

**Independent Test**: Загрузить файлы с известным временем последнего изменения, одинаковыми временами, запоздалой записью и отсутствующим временем; проверить порядок, source label, latest result и status mapping.

**Acceptance Scenarios**:

1. **Given** выбран локальный JSON с доступным `lastModified`, **When** результат принят, **Then** это время используется как время результата и явно маркируется как время последнего изменения файла, а не creation time.
2. **Given** metadata времени отсутствует или невалидна, **When** результат принят, **Then** timestamp результата остаётся неизвестным и timestamp папки не подставляется скрыто.
3. **Given** надёжно распознана ошибка авторизации, **When** показан статус, **Then** пользователь видит «Ошибка авторизации».
4. **Given** ping failure, malformed JSON, read failure, unmatched result или неизвестная ошибка, **When** показан статус, **Then** он не называется ошибкой авторизации и получает отдельную достоверную подпись.

---

### User Story 3 - Анализировать только значимые изменения (Priority: P1)

Администратор получает события только по централизованно выбранным прикладным параметрам категории/производителя, с русскими названиями параметров.

**Why this priority**: Полное сравнение raw JSON создаёт шум от timestamps, runtime metadata и неиспользуемых полей.

**Independent Test**: Импортировать пары результатов с изменением значимого, неанализируемого и служебного поля; проверить события, русские labels, old/new, late arrival и сохранность raw history.

**Acceptance Scenarios**:

1. **Given** изменился подтверждённо значимый параметр, **When** сравниваются соседние результаты, **Then** создаётся change с датой, локацией, устройством, русским параметром, «Было» и «Стало».
2. **Given** изменилось только поле вне активной конфигурации либо служебный timestamp, **When** выполняется diff, **Then** change не создаётся, но raw JSON остаётся доступным.
3. **Given** старый результат добавлен между двумя существующими, **When** история перестроена инкрементально, **Then** заменяется только прежняя соседняя пара и создаются не более двух новых пар.
4. **Given** для категории/производителя ещё нет подтверждённого перечня, **When** результаты сравниваются, **Then** система не выдумывает значимые поля и не создаёт changes из всего raw JSON.

---

### User Story 4 - Быстро импортировать большую SR (Priority: P2)

Администратор импортирует крупную XLSX-выгрузку, видит русские этапы и прогресс, а интерфейс остаётся отзывчивым.

**Why this priority**: Наблюдаемая задержка SR похожа на ранее устранённый нелинейный импорт JSON и будет усиливаться с ростом семи категорий.

**Independent Test**: Выполнить synthetic benchmark до/после на 1 000, 5 000, 10 000 и 25 000 строк, затем загрузить XLSX через `index.html` и сверить inventory.

**Acceptance Scenarios**:

1. **Given** крупная валидная SR, **When** выполняется импорт, **Then** строка нормализуется и классифицируется один раз, а итоговые категории не строятся семью независимыми проходами.
2. **Given** длительная обработка, **When** импорт продолжается, **Then** отображаются этапы «Чтение выгрузки SR», «Обработка строк», «Формирование перечня оборудования», «Обновление аналитики», «Готово» и обработано/всего.
3. **Given** одна ошибочная строка, **When** выполняется импорт, **Then** остальные строки принимаются, а ошибка локализуется на строке.

---

### User Story 5 - Видеть новые категории на Главном экране и в Справочнике (Priority: P2)

Администратор видит компактную разбивку оборудования по семи категориям и достоверные определения правил, времени, статусов и изменений.

**Independent Test**: Импортировать по одному устройству каждой категории, открыть Dashboard и Справочник, сверить counts, drill-down и определения.

**Acceptance Scenarios**:

1. **Given** inventory семи категорий, **When** открыт Главный экран, **Then** компактный блок «Оборудование» показывает семь counts без семи крупных однотипных карточек.
2. **Given** открыт Справочник, **When** выполнен поиск по новым категориям, времени или изменениям, **Then** доступны русские объяснения фактических правил без вымышленных vendor capabilities.

### Edge Cases

- `lastModified` отсутствует, равен нулю, не является конечным числом, округлён браузером или совпадает у нескольких файлов.
- Два результата одного устройства имеют одинаковый timestamp; порядок остаётся стабильным и воспроизводимым.
- JSON classification conflict с категорией SR не переносит устройство в другой пользовательский модуль.
- Один IP соответствует нескольким SR-устройствам.
- Повторная SR меняет категорию существующего устройства.
- Manufacturer/model отсутствуют либо для них нет selective field configuration.
- Auth marker отсутствует или неоднозначен; статус остаётся общей ошибкой обработки/неизвестным, но не auth error.
- Большая SR содержит дубликаты идентификаторов, повторяющиеся IP и неизвестные типы.
- Пассивное оборудование не содержит inventory/serial/MAC/IP; строка всё равно должна присутствовать в своей категории с предупреждением о неустойчивой идентичности.
- Значение «Тип оборудования = controller» не должно перекрывать более конкретную утверждённую категорию из поля «Тип модели».

## Requirements

### Functional Requirements

- **FR-001**: Навигация MUST содержать раскрывающийся родительский пункт «Оборудование» с семью утверждёнными дочерними модулями.
- **FR-002**: Все дочерние модули MUST использовать общий inventory renderer, filters, detail/history и analytics behavior.
- **FR-003**: Категории MUST определяться одним взаимоисключающим классификатором: `Video Conference` → `vcs`, `controller` → `controller`, `Панель управления` → `panel`, `Коммутатор` → `switch`, `Матричный коммутатор` → `matrix_switch`, `Скалер` → `scaler`, `Аудио процессор` → `audio_processor`.
- **FR-004**: Классификация MUST нормализовать регистр и внешние пробелы, сохраняя raw SR значения.
- **FR-005**: Неизвестный тип MUST оставаться `other` и не попадать ни в один из семи рабочих модулей.
- **FR-006**: Новые категории MUST поддерживать существующее IP JSON → IP SR matching без category-specific duplicate logic.
- **FR-007**: Polling capability новых категорий MUST быть `not_implemented/protocol_required` до появления подтверждённого adapter; vendor API/auth MUST NOT выдумываться.
- **FR-008**: Время отдельного browser-selected результата MUST браться из валидного `File.lastModified` и храниться с источником `file_last_modified`.
- **FR-009**: `File.lastModified` MUST описываться как время последнего изменения файла, не как creation time.
- **FR-010**: При отсутствии валидного file timestamp система MUST хранить неизвестное время результата с явным источником `unavailable`; folder timestamp MUST использоваться только для run grouping/identity.
- **FR-011**: UI MUST называть поле «Дата и время опроса» и предоставлять понятное объяснение фактического источника.
- **FR-012**: Хронология MUST поддерживать late arrival, одинаковые timestamps и неизвестные timestamps детерминированно без ложного порядка по folder timestamp.
- **FR-013**: Status projection MUST различать как минимум `success`, `authorization_error`, `network_unreachable`, `processing_error`, `not_polled`, `unmatched` и `unknown`, только когда соответствующий признак доказан.
- **FR-014**: Generic `error` MUST NOT отображаться как «Ошибка авторизации» без надёжного auth evidence.
- **FR-015**: Presentation dictionary MUST предоставлять русские labels для всех доступных status/filter/dashboard/table/history значений.
- **FR-016**: Change detection MUST сравнивать только централизованно объявленные значимые paths для category с optional manufacturer/model specialization.
- **FR-017**: Конфигурация значимого параметра MUST включать стабильный rule ID, JSON path, русское название и назначение.
- **FR-018**: Поля вне выбранной конфигурации MUST сохраняться в raw result, но MUST NOT создавать DeviceChange.
- **FR-019**: Изменение runtime timestamps/metadata MUST NOT создавать change, если поле не включено явно.
- **FR-020**: При отсутствии подтверждённых значимых paths для scope change detection MUST быть пустым, а не переходить к полному raw diff.
- **FR-021**: Late insertion MUST пересчитывать только затронутые соседние pairs с учётом актуальной selective configuration.
- **FR-022**: UI changes MUST показывать дату/время, локацию, оборудование, русское имя параметра, старое и новое значение.
- **FR-023**: До оптимизации MUST быть измерены чтение XLSX, workbook parsing, rows conversion, normalization, validation/inventory build, state clone/serialization, Dashboard selector и измеримый render overhead.
- **FR-024**: SR import MUST выполнять одну нормализацию и одну классификацию строки и избегать полного поиска existing devices/locations на каждую строку.
- **FR-025**: При необходимости SR rows MUST обрабатываться пакетами с cooperative yield и без state update/render на строку.
- **FR-026**: UI MUST показывать русские этапы SR и обработано/всего, если операция активна.
- **FR-027**: Dashboard MUST учитывать семь категорий одним общим проходом и сохранять визуальный приоритет проблем/статусов.
- **FR-028**: Справочник MUST объяснять «Оборудование», четыре новые категории, фактический источник времени, разделённые статусы и selective changes.
- **FR-029**: Производительность MUST проверяться synthetic benchmark на 1k/5k/10k/25k строк без реальной SR.
- **FR-030**: Реализация MUST сохранять единственный прямой `file://index.html` режим, volatile memory и отсутствие внешней передачи.
- **FR-031**: Реализация MUST обновить tests, architecture/ADR/log/reference и не выполнять commit, push или deploy.
- **FR-032**: Родительский пункт «Оборудование» MUST иметь тот же шрифт, что остальные верхнеуровневые модули, быть свёрнутым при открытии инструмента и независимо сворачиваться/разворачиваться даже при активной дочерней категории.
- **FR-033**: Строка SR без inventory/serial/MAC/IP MUST сохраняться как отдельное устройство и отображаться в перечне; отсутствие идентификатора MUST фиксироваться как предупреждение, а не отклонение строки.
- **FR-034**: Для повторного импорта строка без устойчивых идентификаторов MUST использовать детерминированный локальный fallback по локации и описанию оборудования, не объединяя одинаковые экземпляры в одной выгрузке.
- **FR-035**: Более конкретное утверждённое значение «Тип модели» MUST иметь приоритет над fallback-классификацией `Тип оборудования = controller`.
- **FR-036**: Polling JSON MUST выполнять initial lookup по текущему IP во всём актуальном inventory SR без предварительного ограничения открытым модулем; назначение устройства допускается только после проверок FR-038–FR-045.
- **FR-037**: Для любого однозначно сопоставленного устройства Extron, независимо от категории, exact `error = "No credentials were accepted"` MUST давать `authorization_error`; для устройств других производителей и при неоднозначном сопоставлении это значение MUST NOT отображаться как ошибка авторизации.
- **FR-038**: Новый результат опроса MUST сопоставляться только с `ipNormalized` устройств из актуальной SR (`inCurrentSr !== false`); `ipHistory` MUST NOT участвовать в автоматическом выборе кандидата.
- **FR-039**: Current IP index и optional historical IP diagnostics MUST иметь разделённую семантику; обычный matching MUST выполнять O(1) lookup только в current index.
- **FR-040**: Если current IP отсутствует, результат MUST оставаться без `deviceId` со статусом `unmatched`, даже если этот IP присутствует в `ipHistory` одного или нескольких устройств.
- **FR-041**: Если надёжно определённая категория JSON конфликтует с категорией единственного SR-кандидата, результат MUST оставаться без `deviceId` с диагностикой `category_conflict` и MUST NOT влиять на историю, статус, изменения или аналитику SR-устройства.
- **FR-042**: Для подтверждённых внутренних путей `$.ip` и `$.webBlocks['LAN Settings']['IP Address']` система MUST нормализовать доступные IPv4 и сравнивать их с IP имени файла; расхождение MUST блокировать привязку с диагностикой `ip_conflict`.
- **FR-043**: При нескольких current-кандидатах система MAY уточнить выбор только по надёжно определённой категории JSON; если единственный кандидат не получен, результат MUST остаться `ambiguous` без `deviceId`.
- **FR-044**: Переход IP к другому устройству в актуальной SR MUST связывать новый результат с текущим владельцем IP, а не с прежним владельцем из `ipHistory`.
- **FR-045**: Conflict/unmatched результаты MUST сохранять raw JSON и понятную диагностику, но MUST NOT входить в device history, latest result, Dashboard equipment state или DeviceChange.

### Key Entities

- **Equipment Category Descriptor**: Системный category ID, русское название, SR rule, route, future polling capability metadata и analytics participation.
- **Polling Result Timestamp Evidence**: Timestamp результата и его доказанный источник: `file_last_modified` или `unavailable`; folder timestamp остаётся свойством run.
- **Operational Status Projection**: Разделённый технический и пользовательский статус результата/устройства.
- **Analyzed Parameter Rule**: Rule ID, category, optional manufacturer/model scope, JSON path, русское название, rationale и version.
- **SR Import Session**: Ephemeral progress, stage, processed/total, success/error counts и timings.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% контрольных строк семи типов попадают ровно в ожидаемую категорию; неизвестный тип не попадает ни в одну.
- **SC-002**: Семь категорий доступны из одного раскрывающегося пункта, а активная категория визуально определяется без чтения URL.
- **SC-003**: 100% browser-selected результатов с валидным `lastModified` получают этот timestamp и source; без timestamp ни один результат не наследует folder time.
- **SC-004**: Контрольные success/auth/network/processing/unmatched сценарии имеют разные корректные русские labels; ни одна generic failure не показана как auth error.
- **SC-005**: Во всех selective-diff fixtures значимые изменения создаются, неанализируемые и служебные — нет, late arrival меняет не более двух pairs.
- **SC-006**: Импорт SR на 1k/5k/10k/25k показывает близкий к линейному рост; удвоение строк не вызывает четырёхкратного роста без внешней причины.
- **SC-007**: Во время browser SR import progress обновляется между пакетами, а Dashboard вычисляется не более одного раза после завершения.
- **SC-008**: Dashboard counts семи категорий совпадают с прямым подсчётом synthetic inventory.
- **SC-009**: Все существующие regression/runtime/reference/syntax проверки проходят, secret scan не обнаруживает credentials или реальные SR/polling artifacts.
- **SC-010**: 100% синтетических SR-строк без сетевых и учётных идентификаторов отображаются в своих категориях и остаются отдельными устройствами.
- **SC-011**: Навигация «Оборудование» при старте свёрнута, выполняет не менее трёх последовательных циклов раскрыть/свернуть без изменения активного маршрута и не имеет отдельного усиления шрифта.
- **SC-012**: Exact Extron no-credentials fixture получает «Ошибка авторизации», а контрольные generic/ping/processing fixtures — другие статусы.
- **SC-013**: В regression `.100/.102` JSON контроллера `.100` связывается с current-контроллером `.100`, хотя `.100` присутствует в `ipHistory` скалера `.102`; история и последний статус скалера не меняются.
- **SC-014**: При отсутствии current `.100` тот же JSON остаётся `unmatched`, а historical `.100` используется только в диагностических details.
- **SC-015**: Category conflict и internal-IP conflict дают `deviceId: null`, отдельную русскую диагностику и нулевое влияние на показатели целевого SR-устройства.

## Assumptions

- Browser File API не предоставляет creation time; `lastModified` используется только как явно названное время последнего изменения.
- Полный бизнес-перечень значимых параметров не предоставлен; первая версия включает только paths, уже используемые существующей status/analytics/UI логикой, и возвращается владельцу на согласование.
- Для новых категорий polling adapters и analyzed parameter rules могут быть пустыми до получения подтверждённых данных.
- Существующие internal category IDs сохраняются; новые IDs являются стабильными английскими кодами, но в UI не показываются.
- Persistence и изменение trust boundary не входят в scope.
