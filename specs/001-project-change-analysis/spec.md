## Clarifications

### Session 2026-08-03

- Q: Как MVP должен обрабатывать снимок без стабильных идентификаторов? → A: Принимать снимок, вручную связывать его с проектом, а устройства сопоставлять с уровнем уверенности и подтверждением неоднозначных случаев.
- Q: Когда отсутствие устройства в новом снимке считать подтверждённым удалением? → A: Только когда сборщик явно отметил соответствующий раздел полным; иначе показывать возможное удаление.
- Q: Какие форматы входных снимков должен поддерживать первый MVP? → A: Только версионированный формат Extron, основанный на текущем примере.
- Q: Для какого режима доступа проектировать первый MVP? → A: Одна организация с ролями «Администратор» и «AV-инженер».
- Q: Как долго по умолчанию хранить исходные снимки и историю изменений? → A: Три года, срок настраивает администратор.
- Q: Как должен запускаться и где должен работать MVP? → A: Как browser-only приложение на стеке эталона `drthalas/MVP_DEMO`, прямым открытием `index.html` без backend, базы данных и установки зависимостей.
- Q: Где хранить данные browser-only MVP? → A: В versioned `localStorage` с полным JSON backup/restore; сохранность после очистки browser storage не гарантируется.
- Q: Являются ли роли и локальный login границей безопасности? → A: Нет, это только демонстрационное разделение UI; MVP использует исключительно synthetic/sanitized либо явно разрешённые локальные данные.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Обнаружить изменения нового снимка (Priority: P1)

AV-инженер загружает новый снимок логического проекта и получает понятный список изменений относительно предыдущего снимка: какие устройства добавлены, удалены или вероятно заменены, какие поля изменились и насколько надёжно сопоставлены сущности.

**Why this priority**: Это основной пользовательский результат продукта — обнаружение фактического изменения проекта без ручного сравнения JSON.

**Independent Test**: Загрузить два подготовленных снимка одного проекта с известными изменениями имени, IP, MAC и состава устройств и проверить, что каждое изменение представлено одним событием со старым и новым значением.

**Acceptance Scenarios**:

1. **Given** у проекта есть предыдущий полный снимок, **When** загружен новый снимок с тем же `projectId` и изменённым IP устройства со стабильным идентификатором, **Then** система показывает изменение IP того же устройства, а не удаление и добавление.
2. **Given** в новом полном снимке появилось устройство с ранее неизвестным стабильным идентификатором, **When** сравнение завершено, **Then** система показывает добавление устройства.
3. **Given** из нового снимка исчезло ранее известное устройство и сборщик явно отметил раздел устройств полным, **When** сравнение завершено, **Then** система показывает подтверждённое удаление устройства.
4. **Given** устройство отсутствует, но полнота раздела не подтверждена, **When** сравнение завершено, **Then** система показывает возможное удаление и проблему качества данных, не формируя подтверждённое удаление.
5. **Given** снимок не содержит стабильного `projectId`, **When** пользователь загружает его, **Then** система предлагает вручную связать снимок с логическим проектом и не объединяет проекты только по совпадению имени, IP или MAC.
6. **Given** файл соответствует распознаваемой legacy-структуре текущего примера Extron без `schemaVersion`, **When** пользователь загружает его, **Then** система принимает его с назначенной версией legacy-формата и показывает ограничения полноты.
7. **Given** файл содержит неизвестный формат или неподдерживаемую версию схемы, **When** пользователь загружает его, **Then** система сохраняет исходный файл со статусом неподдерживаемого и не формирует недостоверное сравнение.

### User Story 2 - Исследовать историю проекта (Priority: P2)

AV-инженер открывает карточку проекта, просматривает хронологию снимков и изменений и выбирает любые две даты для сравнения.

**Why this priority**: Хронология позволяет установить, когда возникло отклонение и какие изменения сопровождали его.

**Independent Test**: Загрузить не менее трёх датированных снимков одного проекта, выбрать первый и третий и проверить сводный результат независимо от промежуточного снимка.

**Acceptance Scenarios**:

1. **Given** у проекта есть несколько снимков, **When** пользователь открывает карточку проекта, **Then** он видит снимки в хронологическом порядке по `capturedAt`, отдельно от времени загрузки.
2. **Given** пользователь выбрал две даты, **When** он запускает сравнение, **Then** система показывает изменения между выбранными состояниями.
3. **Given** снимок загружен позже, но его `capturedAt` предшествует уже сохранённому снимку, **When** он принят системой, **Then** хронология строится по времени сбора, а затронутые сравнения пересчитываются или помечаются устаревшими.

---

### User Story 3 - Контролировать отклонение от baseline (Priority: P3)

AV-инженер назначает утверждённый снимок baseline и видит, чем текущее состояние отличается от согласованной конфигурации.

**Why this priority**: Сравнение только с предыдущей датой может скрыть накопившийся drift, если нежелательное изменение сохранилось в нескольких последовательных снимках.

**Independent Test**: Назначить первый снимок baseline, загрузить два последующих снимка и проверить, что второй последующий снимок продолжает показывать неустранённое отклонение от baseline.

**Acceptance Scenarios**:

1. **Given** у проекта есть валидный снимок, **When** пользователь назначает его baseline, **Then** система фиксирует выбор и использует его для последующих baseline-сравнений.
2. **Given** текущее состояние отличается от baseline, **When** пользователь открывает проект, **Then** он видит актуальные отклонения независимо от результата сравнения с предыдущим снимком.
3. **Given** пользователь выбирает новый baseline, **When** выбор подтверждён, **Then** история предыдущего baseline и связанных решений сохраняется.

---

### User Story 4 - Проверить и классифицировать изменение (Priority: P4)

AV-инженер фильтрует события, изучает исходные доказательства, подтверждает ожидаемое изменение либо отмечает его как требующее внимания и оставляет комментарий.

**Why this priority**: Обнаружение изменения полезно только тогда, когда пользователь может понять его происхождение и зафиксировать результат проверки.

**Independent Test**: Открыть событие изменения, проверить значения и исходные JSON-пути, изменить статус проверки и убедиться, что решение отображается в истории.

**Acceptance Scenarios**:

1. **Given** сформировано событие изменения, **When** пользователь открывает его, **Then** отображаются сущность, категория, важность, старое и новое значения, даты, уверенность сопоставления и источники данных.
2. **Given** изменение ожидаемо, **When** пользователь подтверждает его и добавляет комментарий, **Then** решение сохраняется без изменения исходных снимков.
3. **Given** сопоставление неоднозначно, **When** пользователь выбирает корректное соответствие или подтверждает замену, **Then** решение используется в представлении истории и остаётся доступным для аудита.
4. **Given** локальная demo-роль не разрешает действие, **When** пользователь открывает соответствующий экран или операцию через обычный UI, **Then** действие скрыто или отклонено, а интерфейс явно сообщает, что это не настоящая граница безопасности.

### Edge Cases

- Повторно загружен полностью идентичный файл.
- Два разных проекта имеют одинаковое имя файла конфигурации.
- Имя проекта изменилось, но стабильный `projectId` сохранился.
- Изменились одновременно имя, IP и MAC устройства.
- Стабильный идентификатор устройства отсутствует или дублируется.
- Несколько устройств имеют одинаковые модель, имя или IP.
- Один снимок содержит противоречивые значения одного поля из разных источников.
- `Connected Devices` и `systemdevs` содержат дублирующиеся либо расходящиеся списки.
- Массивы имеют другой порядок, но те же элементы.
- MAC отличается только разделителями или регистром, имя — пробелами, boolean — текстовым представлением.
- Снимок частичный, повреждённый, содержит неизвестную версию схемы или новый раздел.
- Снимки поступили не по порядку либо имеют одинаковый `capturedAt`.
- Время устройства расходится со временем сборщика.
- Runtime-состояние изменилось, но конфигурация осталась прежней.
- GUI UUID изменился после публикации, хотя физическая панель осталась прежней.
- Контроллер заменён, но логическая комната и проект сохранились.
- Активный baseline приближается к окончанию настроенного срока хранения.
- Browser storage очищен пользователем, открыт другой browser profile или изменён путь к `index.html`.
- Импорт или новый снимок превышает доступную квоту `localStorage`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать одиночный снимок или набор снимков в поддерживаемом версионированном JSON-формате Extron, основанном на структуре предоставленного примера.
- **FR-002**: Система MUST сохранять исходный снимок неизменяемым вместе с контрольной суммой, `capturedAt`, временем загрузки, версией схемы, версией сборщика и источником.
- **FR-003**: Система MUST обнаруживать повторную загрузку идентичного исходного файла и не создавать дублирующие снимки или события.
- **FR-004**: Система MUST проверять структуру, версию схемы, типы данных и полноту разделов снимка до сравнения; предоставленная legacy-структура Extron без `schemaVersion` MUST получать определённую внутреннюю версию с отметкой отсутствующих метаданных, а неизвестный формат или неподдерживаемая версия MUST сохраняться без аналитического сравнения с понятным статусом.
- **FR-005**: Система MUST сохранять отклонённый или частично обработанный снимок с понятным статусом, перечнем проблем и признаками полноты каждого значимого раздела, не блокируя обработку других файлов загрузки.
- **FR-006**: Система MUST преобразовывать входные данные в канонические представления проекта, контроллера, устройств, GUI, эксплуатационного состояния и диагностики.
- **FR-007**: Нормализация MUST устранять незначимые различия формата MAC, регистра, пробелов, boolean-значений, дат и порядка элементов, сохраняя исходные значения и их происхождение.
- **FR-008**: Система MUST объединять подтверждённые дубли одного устройства внутри снимка и сообщать о расхождениях между дублирующими источниками.
- **FR-009**: Система MUST связывать снимки с логическим проектом по стабильному `projectId`, назначенному объекту или комнате; если идентификатор отсутствует, локальный demo-пользователь MUST иметь возможность вручную связать снимок с существующим или новым логическим проектом, а имя файла проекта MUST оставаться изменяемым атрибутом.
- **FR-010**: Система MUST сопоставлять контроллеры и устройства прежде всего по стабильным идентификаторам, предоставленным сборщиком; при их отсутствии система MUST использовать совокупность доступных признаков, присваивать результату уровень уверенности и не считать имя, IP или MAC единственным неизменяемым идентификатором.
- **FR-011**: Каждое автоматическое сопоставление MUST иметь уровень уверенности: точное, высокое, вероятное, неоднозначное или отсутствующее.
- **FR-012**: Неоднозначное сопоставление MUST быть показано пользователю для подтверждения и MUST NOT автоматически превращаться в достоверное изменение атрибута; ручное решение MUST сохраняться для аудита.
- **FR-013**: Система MUST сравнивать новый снимок с предыдущим по `capturedAt`, любые две выбранные даты и текущее состояние с утверждённым baseline.
- **FR-014**: Система MUST выявлять добавление, удаление и вероятную замену контроллеров и связанных устройств.
- **FR-015**: Система MUST выявлять изменения имени, IP, MAC, hostname, subnet, gateway, DNS, DHCP, модели, part number, firmware, версии и revision проекта, состава устройств, GUI UUID и версии GUI.
- **FR-016**: Система MUST объединять несколько изменённых полей одной сопоставленной сущности в согласованное представление изменения, не выдавая её одновременно как удалённую и добавленную.
- **FR-017**: Отсутствующее поле или устройство MUST считаться подтверждённым удалением только если сборщик явно отметил соответствующий раздел полным; при отсутствии такого признака система MUST сформировать возможное удаление с требованием проверки, а ошибка чтения MUST рассматриваться как неизвестное значение.
- **FR-018**: Изменение порядка элементов, форматирования или другого незначимого представления MUST NOT создавать событие изменения.
- **FR-019**: Система MUST разделять события на изменения конфигурации, эксплуатационные события и проблемы качества данных.
- **FR-020**: Система MUST назначать событиям настраиваемую важность с исходными уровнями: критическая, высокая, средняя и информационная.
- **FR-021**: Каждое событие MUST содержать проект, сущность, тип изменения, старое и новое значения, снимки начала и конца, категорию, важность, уверенность и исходные пути данных.
- **FR-022**: Система MUST предоставлять карточку проекта с текущим состоянием, списком контроллеров и устройств, хронологией снимков и событиями изменений.
- **FR-023**: Пользователь MUST иметь возможность фильтровать события по проекту, периоду, сущности, категории, типу, важности, уверенности и статусу проверки.
- **FR-024**: Пользователь MUST иметь возможность назначать и заменять baseline проекта с сохранением истории таких решений.
- **FR-025**: Пользователь MUST иметь возможность пометить изменение как ожидаемое, требующее внимания или ошибочное сопоставление и добавить комментарий.
- **FR-026**: Система MUST сохранять историю пользовательских решений отдельно от неизменяемых исходных снимков.
- **FR-027**: Система MUST корректно включать запоздавшие снимки в хронологию по `capturedAt` и обновлять затронутые результаты последовательного сравнения.
- **FR-028**: Browser-only MVP MUST показывать постоянное предупреждение, что локальные роли не являются настоящей авторизацией, `localStorage` доступен пользователю browser profile и разрешены только synthetic/sanitized либо явно одобренные локальные данные.
- **FR-029**: Система MUST NOT требовать пароли оборудования; обнаруженные секреты MUST быть помечены как проблема безопасности и скрыты из обычного представления, при этом пользователь MUST быть предупреждён, что raw snapshot остаётся внутри локального backup/state.
- **FR-030**: Обязательный MVP MUST NOT зависеть от уведомлений, PDF/CSV-экспорта, прямого опроса оборудования или автоматического изменения его конфигурации.
- **FR-031**: Поддержка форматов других производителей и пользовательская настройка соответствия полей MUST NOT входить в обязательный MVP.
- **FR-032**: Система MUST поддерживать локальные demo-роли «Администратор» и «AV-инженер»: администратор управляет demo users и retention settings, а AV-инженер загружает и анализирует snapshots, работает с baseline и фиксирует решения; role filtering MUST NOT позиционироваться как информационная безопасность.
- **FR-033**: Локальный state MUST иметь retention_days=1095 по умолчанию и настраиваться demo-администратором; retention MUST проверяться при запуске и явном действии, но интерфейс MUST предупреждать, что браузер может удалить данные раньше.
- **FR-034**: При применении локального retention система MUST удалить raw/derived content из state, сохранить минимальную запись удаления и MUST NOT представлять очистку как изменение оборудования; частичное сохранение при ошибке квоты запрещено.
- **FR-035**: Активный baseline MUST NOT удаляться локальным retention без предупреждения и явного решения пользователя; автоматический background retention при закрытом `index.html` не требуется.
- **FR-036**: Приложение MUST запускаться прямым открытием корневого `index.html` через `file://`, работать без backend, network requests, package manager, build step и внешних runtime-зависимостей.
- **FR-037**: Система MUST сохранять versioned state в `localStorage`, валидировать его перед использованием и безопасно инициализировать пустое demo-state при отсутствии сохранённых данных.
- **FR-038**: Система MUST экспортировать полный versioned state в JSON и импортировать его только после полной валидации и проверки доступной квоты, не повреждая текущее состояние при ошибке.

### Key Entities

- **Логический проект**: Контролируемый объект или переговорная со стабильным `projectId` либо зафиксированной ручной связью; содержит изменяемое имя проекта, контроллеры, устройства, снимки и baseline.
- **Снимок**: Неизменяемый результат одного сбора с исходным файлом, контрольной суммой, временем сбора и загрузки, версиями формата и явными показателями полноты значимых разделов.
- **Контроллер**: Управляющее устройство проекта со стабильным идентификатором, serial number, моделью, part number, firmware и сетевыми параметрами.
- **Устройство**: Панель, мобильный GUI или другое связанное оборудование; имеет тип, стабильные и вспомогательные идентификаторы, имя и наблюдаемые параметры.
- **GUI-конфигурация**: Связанный с устройством интерфейс с UUID, типом, версией, адресом ресурсов и состоянием доступности.
- **Нормализованное наблюдение**: Каноническое значение поля в конкретном снимке с исходным значением, путём и показателем качества.
- **Событие изменения**: Различие между двумя состояниями сущности с категорией, важностью, уверенностью и доказательствами.
- **Проблема качества данных**: Ошибка, неполнота или противоречие, влияющее на достоверность снимка или сравнения.
- **Baseline**: Выбранный пользователем утверждённый снимок проекта, используемый для определения накопленного drift.
- **Решение пользователя**: Статус и комментарий к событию или неоднозначному сопоставлению с историей изменений решения.
- **Пользователь и роль**: Участник одной организации с ролью администратора или AV-инженера; роль определяет разрешённые действия, но не позволяет изменять исходные доказательства.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На контрольном наборе снимков система обнаруживает 100% заранее внесённых изменений обязательных для MVP полей и не создаёт ложных событий из-за порядка элементов, регистра, пробелов или формата MAC.
- **SC-002**: Если стабильный идентификатор сохранён, изменение имени, IP или MAC отображается как изменение того же устройства в 100% контрольных сценариев.
- **SC-003**: Ни один контрольный снимок без явного признака полноты соответствующего раздела не порождает подтверждённое удаление устройства или значения.
- **SC-004**: Для 100% событий пользователь может увидеть старое и новое значения, сравниваемые даты, объект, категорию, важность, уверенность и источник данных.
- **SC-005**: Пользователь может загрузить снимок, открыть результат сравнения и определить наиболее важные изменения не более чем за 3 минуты без ручного просмотра JSON.
- **SC-006**: Повторная загрузка полностью идентичного файла распознаётся в 100% контрольных случаев и не изменяет историю проекта.
- **SC-007**: На browser-only контрольном объёме до 10 проектов, 100 устройств суммарно и 10 snapshots общим размером не более 3 MiB сравнение нового snapshot завершается не более чем за 10 секунд и state сохраняется без quota error.
- **SC-008**: Запоздалый снимок занимает корректное место в хронологии и не оставляет противоречащих ей результатов последовательного сравнения во всех контрольных сценариях.
- **SC-009**: Не менее 90% участников приёмочного тестирования правильно различают конфигурационное изменение, эксплуатационное событие и проблему качества данных без дополнительного объяснения интерфейса.
- **SC-010**: Система корректно классифицирует 100% контрольных файлов как поддерживаемый Extron, распознаваемый legacy Extron либо неподдерживаемый формат и не сравнивает неподдерживаемые данные.
- **SC-011**: Во всех сценариях обычного UI demo-роль видит только разрешённые экраны и действия, а предупреждение об отсутствии настоящей безопасности доступно до импорта данных и в settings.
- **SC-012**: При открытом приложении и явном запуске retention данные удаляются по активной локальной политике, удаление регистрируется и не создаёт ложных событий изменения проекта.
- **SC-013**: В согласованном desktop browser приложение открывается двойным кликом по `index.html`, не выполняет сетевых запросов, сохраняет state после reload и восстанавливает его из валидного JSON backup.

## Assumptions

- Основные пользователи MVP — AV-инженеры и специалисты технической поддержки.
- MVP используется локально в одном browser profile; роли администратора и AV-инженера являются только демонстрационными UI-ролями.
- Логический проект представляет объект или переговорную со стабильным `projectId`; имя конфигурационного файла является изменяемым атрибутом.
- Сторонний сборщик в перспективе будет доработан для передачи `projectId` или `roomId`, `capturedAt` в UTC, версии схемы, версии сборщика и доступных serial number устройств; до этого снимки без стабильных идентификаторов связываются с проектом вручную, а сопоставление устройств остаётся вероятностным.
- Предоставленный JSON без `schemaVersion` является исходным legacy-вариантом поддерживаемого формата Extron; его правила распознавания должны быть зафиксированы контрольными примерами.
- Время `capturedAt` является основным для хронологии; время загрузки, устройства и revision проекта хранится отдельно.
- MAC и IP могут изменяться, поэтому не являются единственными стабильными идентификаторами.
- По умолчанию изменение MAC контроллера имеет высокую важность; изменение стабильного hardware ID или вероятная замена — критическую.
- Контрольный объём browser-only MVP — до 10 проектов, 100 устройств суммарно и 10 snapshots общим raw-размером не более 3 MiB; большие объёмы требуют отдельного storage-решения.
- Срок хранения по умолчанию составляет три года, применяется при запуске/ручном действии и не является гарантией сохранности browser storage.
- Карточка проекта, журнал, фильтры и подтверждение изменений входят в MVP; уведомления и экспорт могут быть добавлены отдельными задачами.
- Форматы других производителей и конструктор пользовательского mapping не входят в первый MVP.
- Проектная constitution должна быть сформирована и утверждена до технического планирования.
- В browser-only MVP используются только synthetic/sanitized или явно разрешённые локальные snapshots; production security требует отдельного ADR.
- Приложение следует runtime-паттерну `drthalas/MVP_DEMO`: `index.html`, `styles.css`, `app.js`, `localStorage`, JSON backup, no dependencies.
