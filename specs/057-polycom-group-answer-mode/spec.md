# Feature Specification: Answer mode Polycom RealPresence Group

**Feature Branch**: `codex/secure-local-runtime`

**Created**: 2026-11-16

**Status на 2026-11-24**: реализовано; администратор подтвердил Answer mode Group 300/310/500/700 в обоих направлениях, отдельно по IP и массово; новые write-результаты — confirmed_user_validation

**Input**: Реализовать изменение Answer mode для exact RealPresence Group 300/310/500/700 на основе подключённого Group 310.

## Clarifications

### Session 2026-11-16

- Q: Как менять два независимых поля автоответа в плане? → A: Отдельно для каждого поля.
- Q: Допустимо ли read-only HTTPS-чтение Group 310 с его самоподписанным сертификатом в текущем сеансе? → A: Да, только чтение; настройки не менять.
- Q: Можно ли выполнить контрольный переход Point-to-Point Yes → No и отдельно восстановить Yes? → A: Да, оба перехода; сервер вернул `NOERROR`, web-меню и post-read подтвердили целевое значение без изменения Multipoint No.
- Q: Можно ли выполнить контрольный переход Multipoint No → Yes и отдельно восстановить No? → A: Да; переход No → Yes подтвердился. Немедленный post-read обратной записи временно показывал оба поля No, но последующее read-only чтение и web-меню подтвердили исходные Point-to-Point Yes / Multipoint No без дополнительной записи.
- Q: Можно ли ограничить один план изменением только одного из двух полей? → A: Нет, требуется возможность задать оба поля в одном плане; минимальный двухпараметрический контракт нужно отдельно проверить на Group 310.
- Q: Можно ли выполнить один контролируемый двухпараметрический переход `Yes/No → No/Yes` и отдельно вернуть исходные значения? → A: Да; обе записи вернули по два `NOERROR`, два последовательных post-read и web-меню подтвердили оба целевых состояния, исходные `Yes/No` восстановлены.

## User Scenarios & Testing

### User Story 1 — Изменить автоответ одного Group 310 (Priority: P1)

Администратор выбирает exact Group 310 из актуальной SR по IP и задаёт целевой режим автоответа. Инструмент подтверждает модель и устойчивую идентичность, читает исходное значение, при необходимости делает не более одной записи и сверяет результат повторным чтением. Обычный опрос остаётся read-only.

**Independent Test**: Подтверждённый контракт Group 310 позволяет проверить оба направления одного поля, не меняя соседнее поле.

**Acceptance Scenarios**:

1. **Given** выбран «Не менять», **when** запускается обычный опрос, **then** команды конфигурации не отправляются.
2. **Given** exact Group 310 и подтверждённый контракт записи, **when** администратор явно согласовал конкретный переход, **then** pre-read, максимум одна запись и post-read устанавливают достоверный результат.
3. **Given** неизвестное исходное значение, изменённый web-контракт или несовпадение модели/идентичности, **when** запускается задача, **then** записи нет.

### User Story 2 — Применить тот же контракт к exact Group 300/500/700 (Priority: P2)

Администратор выбирает один IP либо совместимую группу через существующие фильтры. Каждый Group проходит собственные exact model/identity/bundle gates; отсутствие нужного контракта или транспортной совместимости, включая старый HTTP-only Group 300, не разрешает запись. 2026-11-24 администратор подтвердил Answer mode всех четырёх exact моделей в обоих направлениях, по IP и массово; новые write-результаты помечаются confirmed_user_validation. Это не перенос проверки на произвольные прошивки и не изменение исторических JSON.

**Independent Test**: Синтетические проверки для всех четырёх exact моделей и отказ смешанной группы до сети.

**Acceptance Scenarios**:

1. **Given** только совместимые exact Group из актуальной SR, **when** администратор отдельно подтверждает число целей, **then** каждая цель обрабатывается независимо, без автоматического повторения неясной записи.
2. **Given** смешанная группа, неизвестная модель, смена digest SR или дубль IP, **when** запускается план, **then** он блокируется до первой записи.

## Requirements

- **FR-001**: Выбор размещается в существующем блоке Answer mode; «Не менять» не создаёт write-задачу.
- **FR-002**: Два независимых поля Point-to-Point и Multipoint MUST иметь отдельные переключатели «Не менять / Автоматически / Вручную»; выбор одного не должен менять другое.
- **FR-002b**: Администратор MUST иметь возможность указать целевые значения обоих полей в одном плане; одновременно неизменяемые поля не включаются в запись.
- **FR-002a**: После записи инструмент MUST ограниченно перечитать оба поля до устойчивого совпадения цели и неизменяемого соседнего поля; переходное несовпадение не считается успехом и не вызывает повторной записи. Если согласованное состояние не достигнуто за предел времени, результат остаётся неясным.
- **FR-003**: Режим `Do Not Disturb` не смешивается с «Вручную» или «Автоматически»; без отдельного запроса он не предлагается как целевое значение и не перезаписывается молча.
- **FR-004**: HTTPS/443, текущие pre-auth bundle gates, post-auth exact model и serial/MAC обязательны; недоверенный сертификат принимается только с разрешения текущего запуска. HTTP fallback запрещён.
- **FR-005**: Запись допускается только при текущих подтверждённых признаках web-кода и строгой схеме минимального запроса/ответа, проверенной на Group 310. Drift даёт безопасный отказ `management_contract_unconfirmed` без записи.
- **FR-006**: На устройство допускаются pre-read, максимум одна запись, post-read; таймаут/неясный ответ не повторяется автоматически и не объявляется успехом.
- **FR-007**: Один план содержит один action ID; совмещение с другой write-задачей запрещено. Для массовой операции нужно отдельное согласие и повторная runtime-проверка SR digest, IP, моделей.
- **FR-008**: Учётные данные, сессия, сырые web-ответы и текущие значения, раскрывающие приватную информацию, не сохраняются в репозитории или диагностике.

## Success Criteria

- **SC-001**: Контролируемый Group 310 подтверждает точный переход и сохранение соседнего поля; обратный переход выполняется только после отдельного согласия.
- **SC-002**: 100% отказных тестов неизвестного контракта, чужой модели, несовместимого Group 300 и смешанной группы проходят без записи.
- **SC-003**: Ни один тест сетевой неопределённости не вызывает автоматический повтор записи.

## Assumptions

- По [руководству администратора Poly](https://kaas.hpcloud.hp.com/pdf-public/pdf_9126112_en-US-1.pdf) Point-to-Point и Multipoint — независимые настройки со значениями Yes, No и Do Not Disturb. Конкретный web write-контракт этим руководством не установлен.
