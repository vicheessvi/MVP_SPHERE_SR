# Исследование Answer mode Polycom Group

## Актуальный статус — 2026-11-24

Администратор отдельно подтвердил изменение Answer mode для Polycom RealPresence Group 300, 310, 500 и 700
в обоих направлениях, отдельно по IP и массово. Новые write-результаты имеют
`confirmed_user_validation`; исторические JSON сохраняют прежний статус.
Это пользовательская эксплуатационная проверка, а не независимый live-тест
агента всех моделей/прошивок. Ниже сохранены исходные исследования и первоначальные
ограничения; их предварительный статус заменён данным подтверждением, но
model/identity/bundle/HTTPS gates и запрет повтора неясной записи остаются.


## Решение: точные поля и модель

На exact Group 310 после pre-auth Polycom bundle gate и post-auth модели с serial/MAC узко прочитаны два поля `comm.callsetting.callfeatures.autoanswer.answersinglecall` и `comm.callsetting.callfeatures.autoanswer.answermultipointcall`. Исходные коды `Yes` / `No` соответствуют web-меню. Сырой ответ, идентификаторы устройства и учётные данные не сохранены. Официальное руководство Poly описывает отдельные настройки Point-to-Point и Multipoint со значениями Yes, No, Do Not Disturb: https://kaas.hpcloud.hp.com/pdf-public/pdf_9126112_en-US-1.pdf.

## Решение: минимальный web write-контракт

Текущий `main.js` связывает оба поля с `/rest/config`; `processJsonWriteValue` строит `vars` с `name` и `value`, `setConfiguration` отправляет `POST /rest/config`, UI проверяет `result=NOERROR`. На exact Group 310 отдельно разрешены и выполнены контрольные записи одного поля с pre-read и post-read:

- Point-to-Point `Yes → No → Yes`: оба направления дали `NOERROR`, post-read и web-меню совпали, Multipoint оставался `No`.
- Multipoint `No → Yes`: `NOERROR`, post-read и web-меню показали `Yes`, Point-to-Point остался `Yes`.
- Multipoint `Yes → No`: `NOERROR`; немедленный post-read показал **оба** поля `No`, но последующее узкое read-only чтение и web-меню совпали с исходными `Point-to-Point Yes / Multipoint No` без новой записи. Это свидетельствует о переходной несогласованности чтения, а не о доказанном постоянном побочном эффекте. Production-алгоритм должен ограниченно повторять **только чтение** обоих полей до устойчивого результата; запись не повторять.

## Решение о совместной записи

Администратор требует менять оба поля в одном плане. Один POST с двумя `vars` и устойчивой проверкой обоих полей подтверждён на Group 310; последовательные две записи противоречат принципу «максимум одна write-попытка на устройство».

## Контрольный тест двух полей

По отдельным согласиям на exact Group 310 с исходными `Point-to-Point Yes / Multipoint No` один `POST /rest/config` с двумя `vars` установил `No / Yes`, затем другой отдельный `POST` вернул `Yes / No`. В обоих случаях ответ содержал две соответствующие строки `result=NOERROR`, два последовательных узких post-read и web-меню подтвердили результат. После второго теста исходные настройки восстановлены. Это подтверждает один запрос с одним или двумя изменёнными полями; не разрешает другие поля, значения `Do Not Disturb` и перенос локальной проверки на Group 300/500/700.

Для устранения переходного чтения после предыдущего одиночного теста production post-read должен до ограниченного срока требовать два последовательных совпадения целевого поля/полей и неизменённого соседнего поля. Повторять **только чтение**, не команду записи. При истечении срока исход неясен.

Group 300/500/700 сохраняют предварительный write-статус до отдельной эксплуатации; каждый exact model/identity/bundle gate обязателен.
