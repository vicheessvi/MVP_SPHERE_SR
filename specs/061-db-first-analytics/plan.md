# Plan: DB-first analytics

Python stdlib SQLite строит индексируемый read model в той же выбранной БД из прежних порций, с возобновляемой подготовкой. Клиент получает только bootstrap, SQL-агрегаты, страницу и operational SR context для ввода/опросов. Новые импорты имеют отдельный staging и атомарный publish; старый replacement-save из лёгкого клиента запрещён.

## Constitution Check

До и после исследования: source snapshots и файлы не меняются; вычисленные индексы расположены только в выбранной папке; auth/Origin/CSRF сохраняются. Модельные правила событий не расширяются, миллионы строк не пересылаются в браузер. Прямой file fallback сохраняется.

## Research

Два read-only исследования подтвердили: restore собирает все массивы, render ждёт синхронной аналитики; есть spread RangeError и квадратичный mean. Поэтому устраняются причины, а не только повышается лимит.

## Implementation

`mvp_runtime/read_model.py` — нормализованные таблицы, staging, SQL views; `workspace.py/server.py` — охраняемые API и миграция. `runtime/db-views.js` — запросы, bounded UI и графики, `app.js` — интеграция, временный контекст импортов и polling. Страница <=100 строк, response revision/cursor, серверные XLSX-выборки. Число записей не ограничено прикладным потолком.

## Import progress

`import-progress.md`: проценты и ETA — оценки по фазам, не гарантия времени. SR: нормализация 5–60%, staging 60–80%; JSON/logs: проверка до 5%, обработка с порционным сохранением до 80%; публикация БД 80–99%, 100% только после commit и bootstrap. Процент не растёт по таймеру. Скорость измеряется по приросту выполненной работы, при смене фазы уточняется; устаревшая/исчерпанная оценка заменяется на «Рассчитывается». SQLite копирует staging по ключу ограниченными партиями внутри прежней единой транзакции; правила сравнения/дедупликации не меняются. Сервер возвращает progress из памяти текущего административного сеанса без SQL на каждом тикe, <=64 числовых состояний. Терминальные ошибки/отмена не становятся успехом.

## JSON publication lookup

`json-publication-performance.md`: NOT EXISTS использует существующий `rm_idx_observation` явно, чтобы отсутствие/устаревание статистики не превращало equality lookup устройства и времени наблюдения в повторный проход всех опросов. Предикаты, порядок, правила и атомарность остаются прежними. Готовый staging той же revision сохраняется при rollback и переиспользуется после restart; до продолжения не менять SR и не включать force rescan.

## Filter availability and compact analytics reads

`filter-availability.md`: metadata shared cache уведомляет текущего consumer, отдельно обновляет select, не блокирует Apply периода/поиска. До двух аналитических запросов одновременно. Совместимый covering `rm_idx_event_scope` добавляется к существующей БД при prepare, без source reimport или data revision. SR-first lookup и page-keys-before-payload ограничивают чтение больших доказательств текущей страницей. Предел времени запросов и правила аналитики не ослабляются.
