# SpecKit-lite: производительность публикации JSON

Дата: 2026-11-19.

## Цель и причина

Администратор сообщил о публикации 25 614 JSON дольше 30 минут в версии без прогресса. Доступной системной памяти 5,8 ГБ, Python использует CPU. Активная рабочая БД недоступна агенту; эти данные не доказывают точную причину задержки.

На синтетической SQLite 3.53.1 без ANALYZE обнаружен конкретный дефект: correlated NOT EXISTS в rebuild_json_events выбирает primary key только по label, заново просматривая pollingResults для каждого опроса. Узкий существующий rm_idx_observation по label/device/observedAt даёт тот же результат без полного повторного просмотра. ANALYZE в проверке меняет выбор плана, но нельзя полагаться на наличие свежей статистики в новой/растущей БД.

## Объём правки

- Зафиксировать узкий index lookup в том же запросе; предикаты, порядок, clustering, confidence и event rules не менять.
- Старые БД уже получают этот индекс в prepare/init; схема и номер ревизии правил не меняются. Нет чтения оригиналов, новой зависимости, vendor API или сетевой активности.
- Контроль плана и равенства результатов (включая дубли/противоречия), rollback в незавершённой публикации и reuse staging после reopen.
- Замер полной публикации 25 614 синтетических JSON с изменениями и событиями отдельно от подготовки staging; прежний медленный SELECT ограничить диагностическим deadline, не ждать его бесконечно.
- Протокол безопасного применения: не подменять файлы работающего runtime. После контролируемой остановки и обновления повторный выбор той же папки без force rescan должен переиспользовать сохранённые неизменённые партии. Префиксы всё ещё сверяются; байты полного JSON пропускаются только при совпадении всех fingerprint-полей.

## Проверки и границы

Unit plan без ANALYZE, semantic equivalence, reopen и stage fingerprints, полный Python/JS набор. Benchmark работает только с собственной временной SQLite и синтетическими полями. Его время не является гарантией для рабочей БД или подтверждением фактического места зависания администратора. Опросы, настройки устройств, логи и UI-контракты не расширяются.

## Результат

`scripts/benchmark-json-publication.py --polls 25614`: подготовка staging 7,283 с (не включена в публикацию), полная публикация после тестового rollback/reopen — 5,655 с. В БД опубликовано по 25 614 JSON, изменений и расчётных JSON-событий; 85 обновлений progress. Выборка с исправленным индексом — 1,224 с; прежний lookup прерван по безопасному 3-секундному deadline, полное прежнее время не измерено и коэффициент ускорения не заявляется. SQLite 3.53.1, временная локальная БД, 500 синтетических устройств и ~2 КиБ дополнительных безопасных полей на JSON. Это не замер рабочей базы администратора.

246 Python и 242 JS-теста проходят. Отдельно проверены равные/противоречивые наблюдения, отсутствующее SR-устройство, одинаковый результат двух запросов, узкий индекс без ANALYZE, границы партий, атомарный rollback и reuse подготовленного JSON после открытия новой моделью. Схема БД, event rules и исторические JSON не меняются.
