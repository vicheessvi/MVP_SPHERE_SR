# SpecKit-lite: доступность фильтров после загрузки БД

Дата: 2026-11-19.

Администратор подтвердил сохранение SR/JSON/логов, но широкая аналитика завершается timeout, а все шесть SR-списков показывают «Загрузка значений», включая модули с уже полученными таблицами.

В коде найден lifecycle-дефект: pending facets переиспользуется разными маршрутами, но completion callback привязан к маршруту первого запроса. После перехода callback не обновляет текущую форму, а частичный update таблицы намеренно не меняет фильтры. Дополнительно Apply ожидает metadata и блокируется при её отсутствии.

Объём: актуальный consumer общего facet-cache должен получать ответ независимо от первого маршрута. Обновлять только select/status, не сбрасывать введённый текст, фокус или таблицы. Ошибка списков явная и повторяемая, поиск/период применимы без них. Списки читают только SR, не события/историю. Проверить SQL query plans и ограничить конкуренцию тяжёлых views вместо повышения timeout. Правила событий, знаменатели, scope SR/IP/модели и snapshot revision сохраняются. Никакого повторного импорта источников, изменения polling или скрытых копий.

Acceptance: переход до ответа facets, shared cache, устаревшая revision, timeout аналитики при работающих списках, ошибка metadata при работающем Apply, каскад всех шести полей, фокус/текст, навигация. Замер крупных синтетических событий и filtered scope; рабочая БД администратора не используется.

## Реализация

Completion общего facets-cache уведомляет актуальный маршрут, а не владельца первого запроса. `updateDatabaseFilters` обновляет только select/status/retry; текст, фокус и аналитические панели не заменяются. Metadata имеет собственный 10-секундный client deadline и явный retry; Apply периода/поиска не ждёт metadata. Ввод поиска обновляет списки с debounce. После смены revision старые metadata отменяются/игнорируются. Тяжёлые views выполняются максимум двумя lanes; отменённая генерация не запускает оставшиеся запросы.

`rm_idx_event_scope` — совместимый дополнительный частичный индекс только событий: label/device/time/key/IP/kind/validation/gap/known/anomaly. Фильтр SR формируется до индексного поиска событий. Агрегаты используют covering index без чтения больших evidence-payload. Таблица сначала ограничивает page keys, затем получает payload только выбранных <=101 строк (100 + hasNext). Новый индекс добавляется prepare к существующей БД без смены data revision, checksum или переимпорта источников. Подготовка индекса при первом запуске может занять время; исходные SR/JSON/XML не читаются. Тайм-аут 45 с не повышался; критерии допуска, статусы и event rules сохранены.

## Проверка масштаба

Временная SQLite, 5 000 SR-устройств и 1 000 000 синтетических событий, native insert: списки 0,047 с; первая страница 0,265 с; summary 0,610 с; accounted 0,656 с; heatmap 0,781 с; TOP 2,422 с; duration 2,078 с; export-devices page 1,015 с. Срез одной цели 0,016 с; производителя/модели всей выборки 0,656 с. Дальняя страница OFFSET 499950 — 11,266 с: это не обещание мгновенного произвольного глубокого OFFSET. Подготовка синтетической истории заняла 244,81 с и не входит в время готовых views. Время рабочей БД администратора не измерено.

Сравнительный проход без covering index на таком же миллионе: первая страница 9,765 с, summary 10,110 с, heatmap 10,500 с, TOP 12,281 с. Браузерные сценарии проверяют именно задержанный общий facets при смене модулей, все шесть списков, timeout и ошибку metadata, применение периода/модели, отсутствие потери текста и фокуса. Unit-тесты проверяют stale revision, metadata deadline, план covering lookup, semantic equality и добавление индекса без изменения записей существующей БД.
