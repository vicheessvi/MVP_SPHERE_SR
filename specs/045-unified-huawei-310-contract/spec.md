# Feature Specification: Единый контракт Huawei 310

**Feature Branch**: `codex/secure-local-runtime`
**Created**: 2026-11-10
**Status**: Реализовано; read-only настройки обеих Box отдельно подтверждены администратором
**Input**: Bar 310, Box 310 и Box 610 должны использовать один контракт опроса на основе проверенного Bar 310, аналогично общему контракту TE30/40/50/60. Box-результаты пользователь проверит позже.

## User Scenarios & Testing

### User Story 1 — Один контракт для трёх моделей (Priority: P1)

Администратор выбирает любую из трёх точных моделей и запускает привычный опрос. Во всех случаях используется один алгоритм и один идентификатор контракта; результат сохраняет фактическую модель устройства и статус проверки её настроек.

**Independent Test**: Для каждой точной модели синтетический опрос показывает один идентификатор контракта и свою модель.

**Acceptance Scenarios**:

1. **Given** точный Bar 310, Box 310 или Box 610, **When** опрос завершён, **Then** выбран единый контракт и результат содержит точную модель.
2. **Given** другая модель либо суффиксный вариант, **When** формируется план, **Then** единый контракт не применяется.

### User Story 2 — Безопасность и совместимость (Priority: P1)

Единый контракт не ослабляет проверку модели до отправки пароля и после входа; прежние JSON остаются доступными для ручного импорта и сопоставления с SR.

**Independent Test**: Неверная модель блокируется до credentials, а старый результат с прежним модельным ключом сохраняет связь с точной SR.

**Acceptance Scenarios**:

1. **Given** IP отвечает другой моделью, **When** опрос начинается, **Then** учётные данные не передаются и настройки не читаются.
2. **Given** ранее сохранённый JSON одной из трёх моделей, **When** он импортируется, **Then** точное сопоставление и аналитика не теряются из-за переименования транспорта.

### Edge Cases

- Совместимость web-интерфейса по одной модели не подтверждает значения настроек других моделей.
- Отказ одного поля не должен прерывать обычный опрос.
- Подтверждённый Bar не должен помечать Box как подтверждённые.
- Старые `adapterKey` и идентификаторы контракта в готовых файлах нельзя изменять задним числом.

## Requirements

### Functional Requirements

- **FR-001**: Exact Bar 310, Box 310 и Box 610 MUST использовать один transport и один contract ID на основе Bar 310; модельные ключи инвентаря MAY оставаться раздельными для совместимости истории.
- **FR-002**: Проверка точной модели до credentials, после входа и устойчивой идентичности MUST сохраняться для каждой цели.
- **FR-003**: Подтверждённость обычного опроса и настроек MUST оставаться модельной: Bar 310 подтверждён, Box 310/610 настройки предварительны до отдельных проверок.
- **FR-004**: Старые JSON MUST импортироваться без потери точного сопоставления, если их прежние модельные ключи и содержимое валидны.
- **FR-005**: Обычный опрос MUST оставаться read-only; существующая opt-in задача HTTP MUST не расширяться.
- **FR-006**: Секреты, токены и сырые ответы MUST не попадать в Git, аналитику или статус API.

### Key Entities

- **Единый контракт**: transport, contract ID и фиксированные ограничения ресурсов.
- **Модельная цель**: отдельный инвентарный ключ, exact модель и статус проверки.
- **Исторический результат**: исходный model/adapterKey, который не переписывается ради нового контракта.

## Success Criteria

- **SC-001**: Все три синтетические точные модели используют одинаковые transport и contract ID.
- **SC-002**: Ни одна чужая или суффиксная модель не получает credentials по этому контракту.
- **SC-003**: Импорт старых результатов продолжает сопоставлять каждую из трёх моделей с актуальной SR.
- **SC-004**: Bar-статус остаётся подтверждённым, а обе Box остаются предварительными до эксплуатации.

## Assumptions

- Идентификаторы модельных записей каталога сохраняются для совместимости старых файлов; объединяются именно transport и контракт опроса.
- Файлы, уже сохранённые пользователем, не изменяются.
