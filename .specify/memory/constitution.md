# MVP_SPHERE_SR Constitution

## Core Principles

### I. Неизменяемые исходные доказательства

Каждый принятый снимок MUST сохраняться без изменения вместе с контрольной
суммой, временем сбора, временем загрузки, версией схемы и источником. Любое
нормализованное значение и событие изменения MUST ссылаться на исходный снимок
и путь данных, из которых оно получено. Пользовательские комментарии, решения и
baseline MUST храниться отдельно и не могут изменять исходные доказательства.

Rationale: результат аудита должен быть воспроизводимым и пригодным для проверки.

### II. Идентичность предшествует сравнению

Система MUST сначала сопоставить логический проект и сущности, а затем сравнивать
их атрибуты. Стабильные идентификаторы, такие как `projectId`, inventory ID и
serial number, MUST иметь приоритет. Изменяемые имя, IP и MAC MUST NOT быть
единственным основанием идентичности. Каждое автоматическое сопоставление MUST
иметь уровень уверенности; неоднозначное соответствие MUST NOT превращаться в
достоверное изменение без подтверждения пользователя.

Rationale: без устойчивой идентичности изменение адреса невозможно отличить от
удаления, добавления или замены оборудования.

### III. Детерминированная нормализация

Одинаковые входные данные и одна версия правил MUST всегда давать одинаковое
каноническое состояние и одинаковый набор событий. Нормализация MUST устранять
только незначимые различия представления: регистр, пробелы, разделители MAC,
эквивалентные boolean-значения, формат дат и порядок элементов. Исходные значения
MUST сохраняться. Версия правил нормализации MUST фиксироваться для каждого
результата; изменение этих правил MUST сопровождаться проверкой влияния на ранее
сформированную историю.

Rationale: сравнение должно реагировать на изменение смысла, а не форматирования.

### IV. Безопасная работа с неполными данными

Отсутствующее, недоступное или ошибочно прочитанное значение MUST считаться
неизвестным, а не удалённым. Неполный снимок MUST NOT порождать массовое удаление
устройств или параметров. Противоречия между источниками внутри снимка MUST
сохраняться как проблемы качества данных с provenance. Удаление может считаться
достоверным только при подтверждённой полноте соответствующей области снимка или
после явного решения пользователя.

Rationale: ошибки стороннего сбора не должны превращаться в ложные изменения.

### V. Разделение типов событий и объяснимость

Изменения конфигурации, эксплуатационные события и проблемы качества данных MUST
обрабатываться и отображаться раздельно. Общий успех сбора MUST NOT трактоваться
как исправность оборудования. Каждое событие MUST содержать сущность, сравниваемые
снимки, старое и новое значения, категорию, важность, уверенность сопоставления и
исходные доказательства. Правило, сформировавшее событие, MUST быть однозначно
идентифицируемым.

Rationale: пользователь должен понимать, что изменилось, почему система сделала
вывод и насколько этому выводу можно доверять.

### VI. Локальная защита данных, секретов и доступа

Внутренние IP, MAC, hostname, имена пользователей, сведения об оборудовании,
исходные снимки и результаты аналитики MUST считаться чувствительными
инфраструктурными данными. Приложение MUST NOT создавать постоянное внутреннее
хранилище рабочих данных или секретов, кроме описанного ниже проверочного
значения административного пароля. Явно выбранные пользователем исходные и
выходные файлы MAY оставаться в совместимом открытом формате под защитой прав
доступа Windows; приложение MUST NOT создавать их скрытые копии. Production
runtime автоматического опроса MUST использовать установленный Python 3.11+ без
сторонних пакетов, принимать соединения только через loopback и MUST NOT передавать
данные во внешние сервисы, telemetry или CDN. Node.js MAY использоваться только
для development/CI проверок интерфейса.

Device credentials MAY требоваться только автоматическому polling workflow. Явно
выбранный XLSX MAY проверяться в замкнутой памяти вкладки и MAY передаваться только
same-origin loopback runtime активной одноразовой сессии. Пары MUST NOT попадать в
основной state, DOM, plan, snapshots, аналитику, browser storage, постоянное
runtime-хранилище, логи, диагностику, backup или Git. Runtime MUST сверять SHA-256
того же файла до сети, держать нормализованный пул только в памяти текущего job и
очищать его после завершения, отмены или ошибки; старый vault, hardcoded credentials
и иные fallback-источники запрещены. Ошибка импорта или polling MUST скрывать
значения секретов. Доступ к workflow MUST иметь только роль «Администратор МЦТП».

При первом запуске на каждом компьютере администратор MUST задавать собственные
логин и пароль через одноразовую loopback-сессию Python runtime. Runtime MAY
создать только один локальный файл проверочного значения в профиле текущего
пользователя Windows вне каталога проекта и Git. Файл MUST содержать случайную
соль, версию параметров memory-hard KDF и результат проверки пароля, но MUST NOT
содержать открытый пароль, секреты устройств или данные опросов. Создание MUST
быть атомарным и доступным только в ещё не настроенном профиле; повторный запуск
MUST требовать входа. Python runtime MUST проверять вход до доступа к созданию и
запуску плана и к передаче учётных данных устройств. Клиентская проверка MUST
NOT считаться границей защиты. После закрытия runtime пароль и право доступа
MUST исчезать из памяти; изменение или сброс локального проверочного значения
MUST требовать отдельного явного действия пользователя и MUST NOT иметь
автоматического fallback. Доступ к локальному файлу MUST ограничиваться правами
текущей учётной записи Windows; инструмент MUST NOT обещать защиту от владельца
компьютера, который может изменять исходный код или читать собственный профиль.

Rationale: polling требует секретов, но аналитика не должна становиться каналом
их утечки; непостоянный Python runtime отделяет полномочия опроса от данных анализа.
Локальное проверочное значение позволяет задать свой пароль на каждом ПК без
публикации его в Git и без постоянного хранения паролей устройств.

## Ограничения данных и аналитики

- `capturedAt` в UTC MUST определять положение снимка в хронологии; `uploadedAt`,
  время устройства и даты проекта MUST храниться отдельно.
- Каждый формат входного снимка MUST иметь версию схемы и проверяемые признаки
  полноты разделов.
- Запоздавшие и загруженные не по порядку снимки MUST занимать корректное место в
  хронологии и не оставлять противоречащие ей результаты последовательного diff.
- Дубликаты MUST определяться по содержимому, а не только по имени файла.
- Внутренние дубли сущностей MUST объединяться только при доказанном совпадении;
  расхождения MUST сохраняться как проблемы качества.
- Политики важности MUST быть явными и настраиваемыми; значение по умолчанию MUST
  быть зафиксировано в спецификации или плане соответствующей feature.
- Ожидаемый масштаб и срок хранения MUST быть подтверждены до утверждения
  технического плана, если они влияют на архитектурное решение.

## Workflow и контроль качества

- Крупные, рискованные и неоднозначные изменения MUST проходить поток Full
  SpecKit: `specify -> clarify -> plan -> tasks -> implement`.
- Технический план MUST пройти Constitution Check до исследования и повторно после
  проектирования. Нарушение принципа MUST быть явно обосновано в Complexity
  Tracking; необоснованное нарушение блокирует реализацию.
- Каждое правило сопоставления, нормализации и формирования событий MUST иметь
  парные контрольные снимки и ожидаемый результат до реализации правила.
- Обязательные регрессионные сценарии MUST покрывать неполный снимок, дубликат,
  изменение порядка, запоздалую загрузку, неоднозначное сопоставление и замену
  оборудования.
- Проверки MUST подтверждать отсутствие ложного удаления при ошибке сбора и
  отсутствие ложного изменения при незначимом форматировании.
- Изменение схемы, идентичности, правил нормализации или классификации MUST
  сопровождаться оценкой совместимости и влияния на существующую историю.
- Документация, specification, plan и tasks MUST обновляться вместе с изменением
  соответствующих требований или принятых решений.
- Реализация MUST оставаться минимальной для согласованного пользовательского
  сценария; функции за пределами спецификации требуют отдельного решения.

## Governance

Эта constitution имеет приоритет над локальными практиками реализации. Поправка
MUST быть явно согласована пользователем, содержать причину, оценку влияния на
существующие спецификации и данные и при необходимости сопровождаться ADR или
планом миграции.

Версия изменяется по Semantic Versioning:

- MAJOR — удаление принципа или несовместимое изменение обязательного правила;
- MINOR — добавление принципа, раздела или существенное расширение governance;
- PATCH — уточнение формулировки без изменения обязательного поведения.

Каждая спецификация и технический план MUST проверять соответствие актуальной
версии constitution. Code review и итоговый отчёт задачи MUST сообщать о
проведённых проверках и известных отклонениях. Исключение допускается только как
явно документированное временное решение с владельцем и условием устранения.
