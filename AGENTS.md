# AGENTS.md

## Статус проекта

Проект подготовлен к дальнейшему редактированию через ИИ-агента и GitHub SpecKit.

- Видение: `docs/project-vision.md`. Текущая feature: `specs/052-cloudlink-300-log-collection/` (исследование сбора логов CloudLink 300).
- Интерфейс: Windows, HTML5, CSS3, Vanilla JavaScript, browser File/System Access API, vendored SheetJS CE 0.20.3.
- Production runtime автоматического опроса: установленный Python 3.11+ и только стандартная библиотека; `START_MVP_SPHERE_SR.py` открывает авторизованную loopback-сессию.
- Node.js используется только при разработке для JavaScript regression/reference checks и не требуется пользователю.
- Прямой `file://index.html` — ручной импорт и аналитика без сетевого опроса.
- Хранение: только память вкладки/runtime; выбранные готовые JSON пишутся только в указанную пользователем папку; `localStorage`/`IndexedDB` не используются.
- Роль: только «Администратор МЦТП».
- Constitution: версия 4.0.0 в `.specify/memory/constitution.md`.
- Текущая feature: `specs/052-cloudlink-300-log-collection/` (точный экспорт Bar 300 ещё требует проверки; Box 300/600 предварительны).

## Правила работы агента

- Актуальное уточнение feature 047 / ADR-0049 заменяет прежний предел «один IP» только для Answer mode exact TE20, TE30/40/50/60 и Bar 310/Box 310/Box 610: допустим один IP либо фильтры актуальной SR. Один план содержит один action ID, все выбранные устройства обязаны его поддерживать; смешанная группа блокируется до сети. UI показывает число целей и требует отдельное согласие. Runtime повторно проверяет SR digest, уникальность IP и модели; каждый write остаётся per-device pre-read/максимум one-write/post-read без автоматического повтора неясного исхода. Остальные write-задачи сохраняют single-IP/модельные ограничения. Администратор подтвердил оба направления в одиночном и массовом режимах на всех восьми моделях.

Для точных Huawei TE30/TE40/TE50/TE60 разрешён общий guarded transport `huawei_te_web_cgi_v1` с проверкой модели до credentials и после входа. Отсутствие подтверждённого метода или ответа сохраняет `protocol_required`/`unavailable`. Для exact TE30/TE50/TE60 после отдельного evidence review общего read-only контракта этот же fallback включён условно по маркерам текущего bundle и строгой строковой схеме; его эксплуатационный статус предварительный до проверки администратором на каждой модели.
- Exact Huawei Bar 310, Box 310 и Box 610 используют один transport `huawei_310_rest_v1` и contract ID `huawei-310-rest-v1` на базе проверенного Bar 310; три model-key в SR/JSON остаются отдельными для истории. Общий dispatcher до сети выбирает только exact модель, guarded core `mvp_runtime/adapters/huawei_bar310.py` выполняет HTTPS/443, pre-auth model/bundle gates до credentials, session/account с `X-Access-Token`, bounded ресурсы и post-auth модель плюс SN/ESN либо MAC. Обычный опрос трёх моделей подтверждён эксплуатацией и остаётся read-only. Администратор отдельно подтвердил названия и значения настроек и Site name на обеих Box; новые read-only результаты имеют `confirmed_user_validation`, исторические предварительные JSON не переписывать. Отдельные write-задачи: HTTP `enable_http=0` с post-read и Answer mode `autoreply=1|0`; HTTP write Box ещё ожидает проверки, а оба направления Answer mode в одиночном и массовом режимах подтверждены администратором на всех трёх моделях. Telnet не читается/не пишется; `not_exposed` не доказывает закрытый TCP/23. Суффиксные и иные варианты остаются `protocol_required`. Решения ADR-0046/0047/0048/0049.
- Для exact Huawei 310 после model/identity gates разрешены узкие `POST /v1/om/config` + `CfgIDString` для `sitename`, `autoreply`, `synSerTime/ntpGetMode/ntpServerAddr`, `enableWifi/apEnable/isWifiPriority`, `enable_ssh`, `suppotReboot/sleepTime/autoReboot/sleepCloseAPP/autoRebootVal/savePowerMode`. Текущий bundle и строгая схема обязательны, читать только эти ID, не запрашивать Wi‑Fi пароль/SSID. SSH кодирует `1=включён`, `2=выключен`; автоответ после контролируемого цикла Bar «Авто → Вручную → Авто» кодирует `1=автоматический`, `0=ручной`, вопреки статической подписи в части bundle. Неизвестные расписания питания и очистку после перезагрузки не подменять `autoReboot`. Администратор отдельно подтвердил названия и значения новых read-only полей Box 310/610; новые результаты имеют `confirmed_user_validation`, исторические provisional JSON не переписывать. Решения ADR-0045/0046.
- Для exact Huawei 310 `autoUpdate` отражает подтверждённую администратором возможность обновления прошивки по «Сервер → Основные службы → Тип сервера»: «Вручную» = `disabled`, другой доступный в текущем меню сервер = `enabled`. Это доказательство возможности обновления, но не факт уже выполненного обновления. Read-only `GET /v1/om/config/service` и при `serverType=-1` `GET /v1/om/config/auto-config` выполняются только после model/identity/bundle gates; UI fallback `-1 → Вручную` подтверждён на Bar, Box 310/610 администратор проверил отдельно. Не использовать `cloudType` или `autoUpgFlag`, не декодировать неизвестные/невидимые коды. В JSON обязательны `basis=server_type_audit_rule`, `ruleVersion=bar310-server-type-audit-v1`, `meaning=firmware_update_capability`.
- Для exact Bar 310/Box 310/Box 610 отдельные `set_huawei_310_auto_answer_automatic/manual` доступны одному IP либо совместимому набору по фильтрам SR и не сочетаются с HTTP или другими write-задачами. «Не менять» не создаёт action. На Bar 310 оба направления подтверждены контролируемо; администратор отдельно подтвердил оба направления и оба способа выбора на Box 310/610, их Answer mode write теперь `confirmed_user_validation`. Обычный опрос остаётся read-only, статус HTTP write не меняется. Решения ADR-0048/0049.

Обычный опрос и Site name каждой Box ранее подтверждены администратором (`confirmed_user_validation`); это не подтверждение новых настроек. При `autoReboot=1` период `autoRebootVal` остаётся неподтверждённым до отдельного контракта; при выключенном режиме неактивен. Скрытый `suppotReboot` не подменять автоперезапуском. Для TE20 безопасны только `enabletelnet=0` и `enable_http=0`, для TE30/TE40/TE50/TE60 — `enabletelnet=0` и `enable_http=1`; для точных 310-моделей — только `enable_http=0`, без чтения/записи Telnet. Успех определяется повторным чтением модельного значения; TCP listener не входит в критерий. Реальная write-проверка подтверждена для TE20 и TE40; TE30/TE50/TE60 и Box 310/610 сохраняют provisional-статус до контролируемой проверки пользователя, а model/identity/firmware/schema drift блокирует запись.

- Отдельные write-задачи `set_te_family_auto_answer_automatic/manual` доступны одному exact TE30/TE40/TE50/TE60 по IP либо совместимой группе по фильтрам SR, не сочетаются с другими write-задачами. После model/identity на каждом устройстве проверяются маркеры web-формы и точное отображение `autoreply`: `0=automatic`, `1=manual`; pre-read, максимум одна одноэлементная запись, post-read. - Питание exact TE30/TE40/TE50/TE60: на TE40 дополнительно подтверждены read-only поля `rp_shutdown`, `enable_poweron/off`, `poweron/off_hour/minute` в текущем `WEB_GetCfgParamAPI`. - Для одного exact TE20 по IP из текущей SR отдельные задачи `set_te20_http_open/closed` и `set_te20_telnet_open/closed` меняют только выбранный параметр после model/identity gates: `enable_http` либо `enabletelnet` в `{0,1}`, pre-read, максимум одна одноэлементная запись и post-read. `0` — закрыто, `1` — открыто; «Не менять» не создаёт задачу. Задачи могут сочетаться друг с другом только по одному действию на порт, но не с групповым закрытием или Answer mode. - Для одного exact TE20 по IP из текущей SR задача `disable_te20_auto_update` допускает только «Не менять» или «Отключить», не совмещается с другими write-задачами и после model/identity gates читает только `isenableautoupgrade` в `{0,1}`. При `0` запись не отправляется; при `1` допускается максимум одна запись `isenableautoupgrade=0` и точный post-read `0`. Чтение, семантика и эксплуатационная работа задачи на рабочем ПК подтверждены администратором. Другие модели и включение автообновления остаются `protocol_required`.
- Для одного exact TE20 по IP из текущей SR задачи `set_te20_ssh_enabled/disabled` предлагают «Не менять», «Включить», «Отключить» и не сочетаются с другими write-задачами. После model/identity gates читается только `enable_ssh` в `{0,1}`, при необходимости допускается максимум одна одноэлементная запись 1/0 и точный post-read. Администратор подтвердил эксплуатационную проверку включения и отключения SSH на рабочем ПК. Для иных моделей SSH write остаётся `protocol_required`.
- Для одного exact TE20 по IP из текущей SR задача `set_te20_ntp_settings` принимает три независимых выбора: синхронизация `null/true/false`, режим адреса `null/automatic/manual`, имя сервера `null/строка` до 41 символа. `null` означает «Без изменений». После model/identity gates читаются только `synSerTime`, `ntpGetMode`, `timeServer`, при необходимости отправляется максимум один `WEB_SaveCfgParamAPI` с изменёнными CfgItemInt/CfgItemString и точным post-read всех трёх полей. При итоговом отключении NTP режим/сервер не меняются; при режиме «Авто» сервер не меняется; ручной включённый режим требует непустой сервер. Нельзя сочетать с другими write-задачами. Администратор подтвердил корректное изменение всех трёх показателей на рабочем TE20; на другие модели этот результат не переносится.
- Для одного exact TE20 по IP из текущей SR задача `set_te20_power_settings` принимает отдельные nullable поля `suppotReboot`, `sleepTime`, `enableTimeReboot`, `rebootHour`, `rebootMinute`. Список sleepTime ограничен кодами текущего web-bundle `{0,1,5,10,15,30,60}`; `0` — «Никогда». Включение планового перезапуска требует явного времени 00:00–23:59, при выключении время не записывается. После model/identity gates — точное pre-read всех пяти полей, максимум один `WEB_SaveCfgParamAPI` только изменённых CfgItemInt и post-read. Обычный опрос read-only, совмещение с другими write-задачами запрещено. Администратор подтвердил корректную работу новых параметров питания на рабочем TE20; другие модели остаются `protocol_required`.
- Логи: plan schema v3 имеет независимые `collectJson` (default true) и `collectLogs` (default false), оба false запрещены. Папка логов выбирается отдельно в текущем browser-сеансе; exact TE20 после model/identity и bundle gates использует read-only GET `/log?actkn=<session-token>?rmd=<nonce>` через HTTPS/443/TLS1.1; exact TE30/40/50/60 используют только при маркерах текущего bundle отдельный GET `/log?Token=<session-token>?rmd=<nonce>` через HTTPS/443 с обычным модельным TLS-профилем. Администратор подтвердил запросы логов TE20/30/40/50/60. Exact Bar 310/Box 310/Box 610 после собственных pre/post-auth model/identity gates и двух bundle-маркеров могут использовать только `POST /v1/om/log/export`; администратор 2026-11-13 подтвердил корректный опрос и сбор логов каждой модели, новые logCollection результаты имеют `confirmed_user_validation`. XML `LogModule` потоково передаётся по same-origin loopback и пишется браузером только в выбранную timestamp-папку без серверного spool и без содержимого в JSON/status. Иные модели не получают log-запрос без отдельного контракта. В режиме только логов файлы опроса JSON не создаются, но видимый `polling-recovery.json` остаётся в папке логов. Импорт логов считывает только префикс, показывает метаданные и точное сопоставление IP, не исполняет XML и не распаковывает архивы. Администратор также подтвердил событийную аналитику Bar 310/Box 310/Box 610; Box используют отдельные точные версии правил. Подтверждение сбора/анализа не относится к HTTP write.
- Актуализация feature 052 / ADR-0055: exact Bar 300/Box 300/Box 600 после собственных pre/post-auth model/identity gates и двух маркеров текущего bundle используют отдельный read-only `GET /log?rmd=<nonce>` с cookie сеанса, не TE token URL и не REST 310. На Bar 300 проверены HTTP/MIME/XML-префикс и полный поток `LogModule` без сохранения; пользовательское сохранение ещё не подтверждено, поэтому `logCollection.validationStatus=provisional_user_validation` для всех трёх моделей. Box 300/600 live не проверены. Поток передаётся только существующему `on_log`, без server spool, raw JSON/status или нового UI; отсутствие маркеров даёт `protocol_required`. Событийные правила TE/310 на серию 300 не переносить. Это уточняет прежнюю фразу «Иные модели» выше.
- 2026-11-10 администратор подтвердил, что запросы по логам exact TE20/TE30/TE40/TE50/TE60 отрабатывают корректно на рабочем ПК. Это пользовательская эксплуатационная проверка сбора, а не независимое подтверждение агента каждой модели; разбор событий внутри логов и другие модели остаются вне подтверждённого контракта.
- Аналитика логов exact Huawei TE20/TE30/TE40/TE50/TE60: только после ручного импорта общей папки и однозначного точного IP в актуальной SR. Сканировать UTF-8 строки внутри `LogModule` потоково, не требуя корректности всего XML-дерева; сырые строки и секреты не помещать в state/аналитику/backup. Для TE30/40/50/60 `LOG_MOD_MC` + `System start` — запуск, подтверждённая перезагрузка требует соседнего явного `normal ... reboot`, `LOG_MOD_BSP` + `Terminal ... powered ... off` — зафиксированное отключение. Для exact TE20 действует отдельная схема с идентификатором потока: `LOG_MOD_MC` + `System ... boot` — запуск, только пара предшествующего `LOG_MOD_WEB` + `reboots` в пределах двух минут и нового boot подтверждает перезагрузку; `LOG_MOD_WEB` + `shut ... down ... terminal` подтверждает штатную web-команду отключения. Оба TE20-маркера выявлены после отдельных действий администратора; код проверяется на полном логе только в памяти. Никакое отключение не доказывает аварийную потерю электричества. Неясные запуски показывать отдельно, повторные выгрузки дедуплицировать по deviceId/типу/локальному времени, неизвестную схему и неоднозначный IP исключать. TE30/50/60 ожидают пользовательской проверки аналитики. Extron-правило не смешивать с Huawei.
- Аналитика логов exact Bar 310 использует отдельный `huawei-bar310-log-v2`: web-перезагрузка требует успешной web-команды `reboot terminal` и следующего `System boot` в пределах трёх минут; пультовая — двух отдельных `Remote control power button` в пределах 30 секунд и boot в пределах трёх минут без команды выключения. Web-выключение подтверждается своей командой `shut down terminal`; пультовое — `user shut down terminal` в пределах 10 секунд после кнопки пульта. Boot в пределах десяти минут после такой команды показывать как «Запуск после штатного выключения», не как новую перезагрузку. Это штатные действия, не доказательство аварийной потери питания. Внутренние `restart` компонентов, одиночное нажатие и boot без подтверждения не считать перезагрузкой; boot без причины показывать отдельно. Парсить только после однозначного IP в текущей SR и exact модели; сырые строки не сохранять, повторные выгрузки дедуплицировать. Box 310/610 не наследуют событийное правило до проверки их журналов. Решение ADR-0051.
- Администратор 2026-11-13 отдельно подтвердил корректность анализа Box 310 и Box 610. Их события входят в основной индекс Huawei 310 с точными модельными `huawei-box310-log-v1`/`huawei-box610-log-v1` и `confirmed_user_validation`, участвуют в таблицах, кольцевой диаграмме и тепловой карте. Exact модель, однозначный IP текущей SR, формат XML и дедупликация обязательны; прежние provisional результаты не переписывать. Подтверждение анализа не относится к HTTP write.
- Аналитика питания feature 050: внутренние разделы «Анализ перезагрузок» и «Анализ отключения питания» не смешивают события. Только перед неизвестным запуском точных Bar 310/Box 310/Box 610, как и TE20/30/40/50/60, завершённая пауза логов не менее 60 минут по умолчанию даёт низкодостоверное предположение, не подтверждённую потерю питания; известные команды исключают его. Box 310/610 участвуют после отдельного пользовательского подтверждения событийной аналитики. Кольцевая диаграмма берёт 100% от устройств текущего фильтра SR и одно максимальное завершённое наблюдение на устройство, остальные входят в серый сектор. Восемь непересекающихся интервалов длительности: до часа, суток, недели, месяца, 3 месяцев, 6 месяцев, года и более года; месяц = 30 суток, год = 365. Начальный интервал — более года. Подтверждённый интервал от команды выключения до следующего boot и предположительная тишина логов должны иметь разные подписи. Это не текущее состояние питания и не доказательство аварийного отключения. Решение ADR-0052.
- Тепловая карта feature 050: в разделе питания показывать 7×24 ячейки по уникальным устройствам текущих фильтров и выбранного периода. Подтверждённые штатные выключения и предполагаемые паузы переключаются отдельно; число событий и число устройств не смешивать. При нажатии раскрывать SR-устройства, локации, адреса и только метаданные файлов/строк, без сырого текста. День и час брать из локального времени каждого терминала без конверсии или предположения об общем часовом поясе. Совпадение времени не доказывает общую причину.
- После отдельного контролируемого выключения TE20 с пульта администратором подтверждён `LOG_MOD_RC` + `user ... shut ... down ... terminal`; это второй модельный маркер штатной команды отключения с `shutdownMethod=remote_control`, отличимый от `LOG_MOD_WEB` с `shutdownMethod=web`. Нажатия Power, сон, `OFFLINE` и последующий boot сами по себе не являются событием отключения. Полный лог проверен в памяти, реальные строки не сохранялись.
- Новый adapter регистрировать через `mvp_runtime/polling.py` и `runtime/device-catalog.json` только после evidence review, описанного в `docs/development-workflow.md`.
- Не изменять raw SR/JSON и внутренние enum-коды ради локализации; русские подписи брать из централизованного presentation dictionary в `app.js`.
- Термины SR, GCPlus и перезагрузок не трактовать без подтверждения; использовать «Требует уточнения» и «В разработке».
- Для exact Huawei TE20/30/40/50/60 длительная пауза в импортированном журнале перед неизвестным запуском даёт только отдельное низкодостоверное «Предполагаемое отключение питания» при настраиваемом пороге (60 минут по умолчанию). Это не подтверждение физической потери питания, не точное время её начала и не часть подтверждённых счётчиков; TE30/50/60 требуют проверки по реальным логам. Exact Bar 310 использует собственную схему такого предположения по feature 050; остальные модели правило не наследуют.
- Доступные модули, их названия, справочные описания, пользовательские статусы и подсказки изменять через `product-catalog.js`; после правки обязательно запускать `node scripts/validate-reference.js`.
- Не добавлять новый доступный маршрут в обход `MODULE_CATALOG` и не дублировать модульные карточки вручную в `app.js`.
- Никогда не помещать реальные логины, пароли, токены, ключи, IP-выгрузки или runtime data в Git, fixtures, логи, state, аналитику и ответы API.
- Учётные данные вводятся пользователем в форме текущей вкладки и передаются только в same-origin loopback runtime. После передачи поля очищаются; пары нельзя помещать в state, plan, browser storage или постоянное хранилище.
- Runtime сверяет SHA-256 переданных пар, очищает пул во всех terminal paths и выдаёт redacted JSON по одному до ACK записи. Vault и fallback credentials запрещены.
- Доступ к плану на каждом ПК настраивается при первом запуске: локальный scrypt-verifier хранится только в профиле текущего пользователя Windows вне Git, открытый пароль не сохраняется. Python runtime проверяет вход до любого `/api/polling/*`; браузерное скрытие формы не считается границей защиты. Пароли оборудования по-прежнему только в памяти задания.
- Не добавлять внешнюю передачу, CDN, телеметрию, third-party Python dependency или non-loopback bind без явного решения пользователя и security review.
- Не делать commit/push без явного указания пользователя.
- Значимые решения фиксировать в `docs/decisions`, этапы — в `docs/implementation-log.md`.
- При изменении архитектуры, workflow или поведения обновлять документацию и тесты.

## Workflow

Подробности находятся в `docs/development-workflow.md`.

- Full SpecKit — крупные, рискованные или неоднозначные задачи.
- SpecKit-lite — средние задачи.

## Проверки

- Python runtime/API/security: `python -m unittest discover -s python_tests -v`.
- Python syntax/import: `python -m compileall -q mvp_runtime python_tests START_MVP_SPHERE_SR.py`.
- Интерфейс и регрессия: `node tests.js`.
- Справочник: `node scripts/validate-reference.js`.
- Синтаксис изменённых `.js`: `node --check`.
- Secret/artifact/IP scan обязателен перед commit.
- Acceptance: `START_MVP_SPHERE_SR.py` проверяет полный автоматический workflow; прямой `index.html` — ручной пакетный импорт, сеансовую аналитику и блокировку сети.
